# 面试官数字人素材

组件只认下面这几个文件名，**换人不改代码**。

| 文件 | 用途 | 参数 |
| --- | --- | --- |
| `room.webp` | 整屏背景（**虚化版**办公区） | 1920×1280，72 KB |
| `room-sharp.webp` | 背景原图（未虚化，只作生成用的源文件） | 1920×1280，275 KB |
| `listen-loop.webm` | **倾听循环**：闭嘴微笑 + 眨眼 + 轻微点头，ping-pong 无缝 | 620×540，435 KB，alpha |
| `speak-alpha.webm` | **说话素材**（临时）：口型尚未与 TTS 对齐，播完靠 phase 切回 | 620×540，475 KB，alpha |
| `fallback.png` | 视频解码失败时的静态兜底（倾听素材的一帧） | 620×540，194 KB，alpha |
| `base.webp` | 静态人像：Safari / 省流 / 视频不可用时的降级画面 | 640×640，33 KB，**alpha** |
| `idle.webp` | `base.webp` 的源图（原始抠图，闭嘴不露齿） | 640×640，42 KB，**alpha** |
| `speaking.webp` / `listening.webp` / `poster-cut.png` | 旧版素材，当前代码不引用 | — |

人物和背景是两层：背景负责房间，人物（图片或视频）负责表情，叠在一起就是「她坐在这个房间里」。

## 两条渲染路线

`VideoInterviewer` 会先探测能力，再决定走哪条：

| 路线 | 触发条件 | 画面 |
| --- | --- | --- |
| **视频**（默认） | Chromium / Firefox，且未开省流 | 透明 webm 叠在 `room.webp` 上，会眨眼、点头、说话时动嘴 |
| **静态**（降级） | Safari / iOS、`saveData`、素材 404 或解码失败 | `base.webp` + 0.6% 呼吸缩放 |

Safari 一律判死的原因：它能解 VP9，但**不认 VP9 的 alpha 通道**（那是 Chromium / Firefox 的实现）。
alpha 一丢，透明区会渲染成黑底方块，比静态图难看得多。宁可主动降级，不赌 UA 边界情况。

两条路线的落位常量（`LIFTED_BOX` / `FINISHED_BOX`）是同一份，从 `DigitalInterviewer.tsx` 导出，
避免降级切换的瞬间人像跳位。

## 视频素材怎么来的

源片是即梦生成的 960×960、24.12 fps、h264。逐条验收结论：

| 原片 | 时长 | 背景 | 口型 | 用途 |
| --- | --- | --- | --- | --- |
| `2428` | 5.02 s | 全片绿幕 `#56D062` | 闭口（眨眼 + 一次点头） | ✅ `listen-loop.webm` |
| `4845` | 10.02 s | 前 2.5 s 木纹，之后绿幕 `#54D75D` | 3 s 后开口 | ✅ `speak-alpha.webm`（取 3.2 s 之后） |
| `6351` / `3854` | 10.02 s | 木纹（咖啡馆） | — | ❌ 抠不干净，弃用 |

生产命令（三步，参数不可随意改）：

```powershell
# ① 导出带 alpha 的帧序列
ffmpeg -i 2428.mp4 `
  -vf "crop=960:836:0:0,chromakey=0x56D062:0.08:0.03,despill=type=green:mix=0.8,scale=620:-1" `
  -fps_mode passthrough -pix_fmt rgba seq-fwd/f%04d.png

# ② 拼 ping-pong（1..N + N-1..2），脚本：tmp/live2d-web/pingpong.py
python pingpong.py

# ③ 从序列编码
ffmpeg -framerate 24.12 -i seq-loop/f%04d.png -vf format=yuva420p `
  -c:v libvpx-vp9 -pix_fmt yuva420p -crf 34 -b:v 0 -auto-alt-ref 0 -an listen-loop.webm
```

### 六个坑（每个都踩过）

1. **绿幕色每条都不一样**：2428 是 `#56D062`，4845 是 `#54D75D`。用标准 `#00B140` 抠，人物会整片半透明。
2. **ffmpeg 9 删掉了 `-vsync`**，改 `-fps_mode passthrough`。不加这参数，5.02 s 的片子会被容器声明的 60 tbr 填成 303 帧（真实 121 帧），节奏全乱。
3. **`reverse` + `concat` 会丢 alpha**：即使中途加 `format=yuva420p`，重编码后 alpha 也消失（实测三次）。ping-pong 必须走「PNG 序列 → 拼 → 编码」。
4. **`-auto-alt-ref 0` 不能省**，否则 Chrome 不认 VP9 的 alpha。
5. **`ffprobe` 看不出有没有 alpha**，一律报 `yuv420p`（alpha 存在独立的 BlockAdditional 里）。判断只能在浏览器里实测。
6. **片头片尾的几帧抠不干净，会在循环里「闪」**。这条最坑，因为预览动图看不出来，上线后每循环一次闪一下。

### 第 6 条展开：为什么开头会闪过一块

即梦的片子不是一上来就绿幕满屏——开头几帧是淡入的，绿幕还没铺满整幅画面。`chromakey` 面对这种画面只能抠掉一部分，出来的帧**透明率只有 0~24%**（正常帧约 44.6%），叠到页面上就是**一块不透明的方块闪一下**。

实测 2428 原始 121 帧的透明率分布：

| 帧号 | 透明率 | 说明 |
| --- | --- | --- |
| 1–2 | **0.0%** | 完全实心，抠像完全没生效 |
| 3–11 | 9.5% → 24.6% | 淡入中，抠不干净 |
| 12–110 | 44.4% ~ 45.2% | ✅ 干净 |
| 111–121 | 24.6% → 0.0% | 淡出，同开头 |

`4845`（说话素材）也一样：从 3.2 s 切进去，头 11 帧照样不干净，必须从 **3.78 s** 才开始。

**做法**：裁掉首尾，让每一帧都达标。用 `check_alpha.py` 当守门员：

```powershell
# ① 带 -ss/-t 裁到干净段再导出
ffmpeg -i 2428.mp4 -ss 0.55 -t 4.0 `
  -vf "crop=960:836:0:0,chromakey=0x56D062:0.08:0.03,despill=type=green:mix=0.8,scale=620:-1" `
  -fps_mode passthrough -pix_fmt rgba seq2/f%04d.png

# ② 任何一帧透明率 < 35% 就报错，别往下走
python check_alpha.py seq2

# ③ 拼 ping-pong 后**再查一次**（拼接会把首尾帧翻倍，坏帧会出现在两头）
python pingpong.py seq2 seq2-loop
python check_alpha.py seq2-loop
```

当前达标的素材：

| 文件 | 帧数 | 透明率范围 | 时长 | 说明 |
| --- | --- | --- | --- | --- |
| **`listen-loop-v3.webm`** | **121（crossfade 闭环 K=10）** | **48.7% ~ 49.1%** | **5.02 s** | **当前使用** |
| `listen-loop-v2.webm` | 39（运动补偿 + 闭环） | 42.5% ~ 46.3% | 1.62 s | 旧素材，留作回滚 |
| `listen-loop.webm` | 39 | 43.9% ~ 45.2% | 1.62 s | 更旧，留作回滚 |
| `speak-alpha.webm` | 142 | 44.1% ~ 44.5% | 5.9 s | 口型未与 TTS 对齐 |

> 文件名带 `v2` / `v3` 不是洁癖：`listen-loop.webm` 这个 URL 已经被浏览器缓存过，
> 换内容不换名的话，用户刷新也还是旧片子。素材有实质修改就换文件名。

> 旧版本文档这里写过「别用 `libvpx-vp9 -pix_fmt yuva420p`，alpha 会被静默丢掉」。
> **那条结论不准确**：alpha 丢失的真正原因是第 3 条（`reverse`/`concat` 路径）和第 4 条（漏了 `-auto-alt-ref 0`）。
> 命令本身是对的，现在几个 webm 都是这条路生成的，浏览器里透明正常。

### 素材准入标准（2026-11-13 定）

换过三条素材才总结出来的。**先量这三个数，再决定要不要开视频路线**：

| 指标 | 合格线 | 测法 |
| --- | --- | --- |
| 头发重心垂直跨度 | < 3 px | 只取画面上半（y<300）、亮度<70 的像素算重心 |
| 末帧→首帧位移 | < 3 px | FFT 互相关，`make_loop.py` 会直接打印 |
| 坏帧（透明率 < 35%） | 0 个 | `check_alpha.py` |

三条都过，`USE_VIDEO = true` 才成立，`K=10` 就够闭环。

三条里任一条不过，说明素材内部在漂移——**crossfade 救不了速度突变**，
这时要么做运动补偿（只能压跨度，救不了观感），要么退回静态图。

当前 `listen-loop-v3.webm` 的实测：

```
源素材 960×960 / 24.12 fps / 5.02 s / 121 帧
头发重心跨度  1.4 px
末帧→首帧位移 (0, 0)
坏帧          0 个（全程透明率 48.7%~49.1%）
页面内实测    相邻采样最大跳变 1.74 px   ← 旧素材是 8.97 px
```

> 这条素材是即梦「图生视频」用绿幕首帧出的，背景是纯 `#00B043`，一次抠干净。
> 关键是提示词里写死了「头部位置完全固定，像证件照一样稳定」——
> **素材的质量在生成那一刻就定了，后期只能补救，不能创造。**

### 第 7 条：旧素材（2428）只有 1.62 秒是能用的

2428 全长 5 秒，但**从头到尾是一个单向长镜头**：半闭眼 → 逐渐睁开 → 平视 → 又开始垂眼。
逐帧看图定出的边界（1-indexed）：

| 帧段 | 状态 | 能用吗 |
| --- | --- | --- |
| 1–33 | 半闭 / 垂眼，逐渐睁开 | ❌ 像没睡醒 |
| **34–72** | **睁眼、平视、微笑** | ✅ 只有这 39 帧 |
| 73–96 | 又开始垂眼（像在打瞌睡） | ❌ |

所以「把低头那段去掉」之后，剩下的只有 **1.62 秒**。

### 第 8 条：crossfade 治不了「内部漂移」

这是最容易踩的坑。把接缝做成 `diff = 0.00` 之后，画面**仍然会跳**——因为
crossfade 只保证「末帧的数值 == 首帧的数值」，但这段素材**内部头部一直在下沉**：

```
画面实测（浏览器里逐帧读像素，FFT 互相关求位移）：
    修改前   dy 跨度 14.7 px，相邻最大跳变 8.97 px   ← 用户看到「头突然跳上去」
    修改后   dy 跨度  5.0 px，相邻最大跳变 3.00 px
```

原因：1.62 秒里头往下沉了 12~14 px，循环时必须把这 12 px 还回去。
crossfade 只用最后 6 帧还账，等于**把 1.6 秒的位移压缩成 0.25 秒的跳动**。
接缝数值是 0，位移速度却是 5 倍——眼睛看的是速度，不是数值。

**正解是先做运动补偿，再闭环**：

```python
# ① FFT 互相关求每帧相对首帧的平移量
cross = np.fft.rfft2(cur) * np.conj(np.fft.rfft2(ref))
corr = np.fft.irfft2(cross / (np.abs(cross) + 1e-8), s=(H, W))
dy, dx = np.unravel_index(np.argmax(corr), corr.shape)   # 峰值位置 = 平移量

# ② 中值平滑（互相关会被眨眼带偏，见过 +16 的孤立尖峰）
# ③ 每帧朝反方向平移回去，让头在整段里保持不动
# ④ 对齐之后再 crossfade 闭环，此时首尾本来就一样，融合几乎无副作用
```

补偿后画面边缘会空出一圈（最大 12 px 的透明带），实测不影响观感——人物头顶本来就在
透明区，肩膀下沿被作答条压住。但**补偿后的帧必须重新跑 `check_alpha.py`**，
透明率会从 44% 掉到 42.5%，仍在阈值之上。

闭环融合仍然要 12 帧（`K=12`）：补偿后残留约 10 px，摊到 12 帧里每帧不到 1 px。


## 状态映射

**当前走视频路线**（`VideoInterviewer.tsx` 里 `USE_VIDEO = true`）：

| `phase` | 画面 |
| --- | --- |
| `PREPARING` / `LISTENING` / `THINKING` | `listen-loop-v3.webm` 循环（5.02 s，无缝） |
| `SPEAKING` | `speak-alpha.webm`，240 ms 交叉淡入；`phase` 离开后淡回倾听 |
| `FINISHED` | 沿用 `FINISHED_BOX` 落位，人像压到画面下沿 |

静态图兜底（`USE_VIDEO = false`，或浏览器不支持 VP9 alpha / 开了省流 / 素材 404）：

| `phase` | 画面 |
| --- | --- |
| 全部 | `base.webp`（640×640，睁眼平视微笑）+ 0.6% 呼吸缩放 |

视频路线的三条实现约束（别碰）：

1. **视频永远静音**。声音走 `useInterviewerSpeech`（AudioContext 播 TTS），视频只提供画面。
2. **倾听视频永不暂停**，`SPEAKING` 时只降到 `opacity: 0`。一旦 `pause()`，切回来会从第一帧重来，眨眼动作会「跳」一下。
3. **不能用 `display: none` 隐藏**，Chrome 会暂停不可见的 video，第 2 条立刻失效。只能 opacity + `pointer-events`。

## 为什么退回静态图（2026-11-13）

视频路线做了三版，全部败在同一个问题上：**这条素材是一个单向长镜头，做不出能看的循环。**

| 版本 | 做法 | 结果 |
| --- | --- | --- |
| v1 | ping-pong（正放 + 倒放） | 动作方向整体反转，像在「来回摆头」 |
| v2 | 5 段不同起点拼接，10.1 秒 | 段落边界能藏，但低频的「整体节奏」还是被看出来 |
| v3 | 运动补偿 + crossfade 闭环，1.62 秒 | dy 跨度 14.7→5 px，但头部仍在缓慢上下浮 |

根因在素材：2428 全长 5 秒，抠像可用 4 秒，**头从第一帧到最后一帧一路下沉 12~14 px，中途不回头**。
所以任何循环都必须把这 12 px 还回去，而「还账」的那一刻就是观众看到的跳。

三个必须记住的结论：

1. **crossfade 只对齐数值，不对齐速度**。接缝 `diff = 0.00` 时画面照样跳，因为位移速度突变了 5 倍。
2. **运动补偿治得了位移，治不了观感**。把 dy 压到 5 px 之后，头变成「极缓慢地上下浮」，比跳更怪——像在水里。
3. **素材的信息量决定上限**。5 秒单向素材能提取的「循环素材」不足 1 秒，而 1 秒的循环里只要有 5 px 以上的位移，人眼就能抓到节拍。

**要重启这条路线，先重新生成素材**，规格见下。静态图是目前唯一稳定的选择：
不说话时它是一张会呼吸的照片，说话时嘴不动——但至少不跳。

### 重新生成素材的规格（给即梦）

| 项 | 要求 | 为什么 |
| --- | --- | --- |
| 时长 | **20~30 秒** | 5 秒是根本瓶颈 |
| 背景 | 纯绿幕，**第一帧就是绿幕** | 淡入段抠不干净，会闪方块 |
| 动作 | 循环眨眼、极轻微点头，**头部不许单向漂移** | 漂移=循环必跳 |
| 机位 | 完全固定，正脸，头部不转动 | 转动无法用平移补偿 |
| 分段 | 同一段里「头回到初始位置」至少 3 次 | 提供可用的循环点 |
| 输出 | 1080p、25 fps、mp4 | |

拿到这样的素材，`listen-loop` 可以切出 3~4 个 6~8 秒的自然循环，前端随机轮播，周期彻底打散。


## 为什么最初是静态表情

中间试过按语音音量驱动口型（底图 + 半张 / 张大两张口型图层，按音量切档），但源素材
只有 AI 生成的几帧，帧与帧之间嘴型对不齐，动起来反而更出戏。所以第一版只保留一张闭嘴微笑：

- 表情不跟着声音变，说话时完全不动嘴；
- 唯一的动效是 0.6% 的呼吸缩放（`.interviewer-breath`，9 秒一轮）。

这一版被视频循环取代了——眨眼和头动是真人感的来源，静态图给不了。

素材是 `idle.webp`：正脸、闭嘴、不露齿的浅笑。

生成脚本（需要 `pillow`、`opencv-python`）：

```powershell
python frontend/scripts/build-interviewer-sprites.py
```

## 背景为什么是虚化的

原图里沙发上坐着三个人，很抢戏。局部的处理：

```
BLUR = 18   SATURATION = 0.82   BRIGHTNESS = 1.02   CONTRAST = 1.08
NOISE_SIGMA = 1.6
```

- `BLUR = 18` 是在 1920 宽下算的，铺到 1440 视口等效约 13.5px —— 人还在，但只剩轮廓。
- 最后加的 `NOISE_SIGMA = 1.6` 是抖动噪点，只为了打散柔渐变在屏幕上的色带，肉眼看不出颗粒。
- 改参数重跑即可，不要手改 `room.webp`：

```powershell
python frontend/scripts/make-room-background.py
```

页面上的白色薄纱（`from-white/60 via-white/30 to-white/5`）是配合虚化背景调过的，
如果换回 `room-sharp.webp`，要把薄纱调回原来的 `72 / 35 / 5`，否则文字会和背景抢。

## 人物落位：两种

| 场景 | 落位 | 下沿怎么处理 |
| --- | --- | --- |
| 面试进行中（作答条在场） | `top-7 bottom-20` | 比作答条上沿低 18px，藏在条后面 |
| 面试已结束（作答条收起） | `top-7 -bottom-[10%]` | 直接溢出视口 |

作答条高度约 98px，人物 `bottom-20`（80px）压进条后面 18px：上沿一条直线横切过外套会很明显，
压进去之后就只剩「她站在输入框后面」。

视频素材是 620×540（31:27），不是方图，所以容器用 `aspect-[31/27]`；
静态降级路线仍是 `aspect-square`（`base.webp` 是方图）。

- `left-1/2 -translate-x-1/2`：水平居中。
- 阴影用 `filter: drop-shadow()`，跟着 alpha 走，是「人」的影子不是矩形影子。
  偏移收到脚下（`0 18px 26px`），之前 `-14px 22px 34px` 那种往左下甩的大投影是「贴纸感」的主要来源。
- 定位和微动必须拆成两层：`animation` 的 `transform` 会覆盖 `-translate-x-1/2`，
  写在同一层人物会往右跳半个身位。

## 用 rembg 抠静态帧（静态素材路线）

```powershell
pip install rembg onnxruntime

# 模型要手动放，rembg 内置下载在国内经常卡死：
#   https://github.com/danielgatis/rembg/releases/download/v0.0.0/u2net.onnx
#   -> %USERPROFILE%\.u2net\u2net.onnx
```

```python
from rembg import new_session, remove
from PIL import Image

sess = new_session("u2net")
frame = Image.open("frame.png").convert("RGB")
cut = remove(frame, session=sess)        # 不要加 post_process_mask，会把软边二值化
cut.save("frame-rgba.png")
```

要点：**不要用 `post_process_mask=True`**，它会把 alpha 二值化，头发边缘变成硬切。
