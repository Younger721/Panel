# 知识库自动归类：准确率专题

> 起因：一道「数据库的存储引擎有哪些？」被挂到了 `后端 / JVM / 内存结构与对象布局`。
> 错得离谱，而且界面上标着「待确认 72%」，看起来像是模型很自信。

## 1. 为什么会错

题面答案里写着：

> MySQL 常见存储引擎有 InnoDB、MyISAM、**Memory**、CSV 和 Archive。

这句话里有两个干扰：

- 「存储引擎」→ 目录树里**没有**这个节点；
- 「Memory」→ 目录树里有 `JVM / 内存结构与对象布局`。

当时的分类器把 **181 个叶子节点**一次性塞进 prompt，让模型做 181 选 1。在这种规模下，
模型遇到一个词面对着像的选项就会抓住它——这是候选集过大时的典型退化，不是"模型不懂 MySQL"。

**证据**：同一道题，清掉挂载后重跑，模型答到了 `后端 / MySQL / 存储引擎`，置信度 0.86。
同一输入、同一模型、两次答案不同，说明是采样波动，靠打磨提示词治不好。

还有两个放大问题的细节：

| 细节 | 后果 |
|---|---|
| `AUTO_APPLY = 0.72`，判断是 `>=` | 模型自己给 0.72（没把握）也照样写库 |
| `apply()` 只清 `primaryFlag`，不删旧行 | 同一道题能同时挂在两个目录下，覆盖率重复计数 |

## 2. 目录本身的问题：97.7% 的节点没有说明

```
kb_category 219 个节点，description 为空的 214 个
```

模型看到的是这样一行：

```
- id=136 | 后端/mysql/慢查询与优化 | 慢查询与优化
```

「慢查询与优化」和「执行计划与索引失效」的区别，靠这行字无法判断。人也要想一下，
何况模型还同时在读另外 180 行。

## 3. 改法：先缩范围，再选，最后兜底

### 3.1 一级/二级目录写说明

6 个一级 + 30 个二级，每条写清"放什么、不放什么"：

```
MySQL        MySQL 本身：索引与 B+ 树、执行计划、事务与隔离级别、MVCC 与锁、
             慢查询、存储引擎、主从复制、分库分表、表设计。
消息队列      消息中间件：可靠性（不丢不重）、顺序、积压、事务消息、延迟消息、
             Kafka 与 RocketMQ 的差异。
```

关键在"不放什么"——它同时告诉人和模型边界在哪。

### 3.2 两阶段分类：先定主题，再挑叶子

```
① 主题词命中？──是──→ 直接锁定主题（不问模型）
                └─否──→ 模型在 30 个二级主题里选
② 同文档兄弟已定主题？──是──→ 跟着走
                      └─否──→ 模型在该主题内的 6~10 个叶子里选
③ 域锚词守卫：选串了就打折，宁可留空
```

三个设计点：

**主题词优先**。技术八股的主题是封闭集合，`mysql / innodb / 索引失效 / 存储引擎`
这类词出现时不需要问模型。确定性的东西交给确定性的代码。

**标题算三分，正文算一分**。一道「消息队列如何确保消息不丢失？」的答案里常拿
Redis 的 AOF 当反例；若标题与正文同权，Redis 会靠两个词的堆叠赢走整道题。
实测这道题从 `redis/分布式锁 0.82` 回到 `消息队列/消息可靠性 0.95`。

**同文档兄弟跟随**。切片标题经常只有「详细解析」「常见风险」，单看自己看不出主题。
一篇文档通常只讲一个主题，跟着同文档里已定下来的兄弟走即可。
修好了「Redis 看门狗」那题 4 个切片被拆到两个域的问题。

### 3.3 第二阶段禁止新建目录

两阶段刚上线时踩的坑：候选只剩五六条时，模型一"觉得都不像"就返回 `path`，
而 `path` 是从根节点开始拼的，于是库里凭空长出三个平行根节点：

```
网络 / http / 断点续传
数据库 / mysql / 慢sql排查与优化
消息队列 / 消息可靠性
```

修法：第二阶段传 `allowNewPath=false`——主题已经定了，只能在主题内的叶子里选，
或者返回 null 交给人。新建目录只允许发生在第一阶段（那里候选是 30 个主题，判断依据充分）。

### 3.4 域锚词守卫（事后兜底）

命中了主题词、但归属路径一个都不沾 → 置信度对半砍：

```
「数据库的存储引擎有哪些？」
  文本命中 mysql 组 → 路径 后端/jvm/内存结构与对象布局 不含 mysql
  0.72 ÷ 2 = 0.36 < 0.72 → 不挂，留在未分类
```

### 3.5 人工优先 + 一条归属

- 已 `locked` 的归属，自动归类一律跳过（人已经表态了）；
- 写新归属前先删旧行（否则同一题能躺在两个目录里）。

## 4. 实测

同一批数据（25 个切片 + 6 道题），三种方案各跑一遍：

| 题目 | 181 全量候选 | 词表收窄 | 两阶段 + 描述 |
|---|---|---|---|
| 数据库的存储引擎有哪些？ | JVM/内存结构 ✗ | mysql/存储引擎 ✓ | mysql/存储引擎 ✓ |
| 消息队列如何确保消息不丢失？ | 0.99 | 0.92 | **0.95** |
| 大文件下载中断后如何继续？ | HTTP/1.1 0.75 ⚠ | 断点续传 0.99 | 断点续传 0.78 |
| Redis 看门狗那题 4 个切片 | 拆到 2 个域 ✗ | 拆到 2 个域 ✗ | **redis/分布式锁 4/4** ✓ |

- 根节点稳定在 6 个（第二阶段禁止新建之后）；
- 一题多挂：0 条；
- 未分类：6 条 —— 宁可留空，也不错挂。

## 5. 描述覆盖情况

```
222 个节点，description 全空 → 222/222 已填
  6 个一级 + 30 个二级：人工撰写，写清"放什么、不放什么"
183 个三级叶子：模型按父级分组批量生成（同一组内互相划界），人工抽查
```

叶子的写法是"具体技术要点"而不是"本目录包含…"，例如：

| 叶子 | 说明 |
|---|---|
| 索引与 B+ 树 | B+ 树结构、聚簇与二级索引、最左前缀、覆盖索引 |
| 执行计划与索引失效 | EXPLAIN 各列、隐式转换与函数致失效 |
| 消息可靠性（不丢不重） | 发送确认、副本刷盘、位点提交、生产幂等 |
| 断点续传与 Range 请求 | 206 与范围响应、校验器防文件变更、分块下载与合并 |
| 混合检索（关键词+向量） | BM25 与向量融合、RRF、权重归一化，不放重排 |

平均 23 字，最长 37 字。写在库里，界面上点中节点就能看到（`KbCatalogPage` 的节点详情）。

## 6. 目录重复的清理

清理前有三处同义或近义节点，会让模型（和人）在两个几乎一样的名字之间乱选：

| 节点 | 处理 |
|---|---|
| `消息队列 / 消息可靠性`（544） vs `消息可靠性（不丢不重）`（153） | 删 544（空节点，且它的说明本身写着"不放具体防丢防重机制"——作为目录没有意义） |
| `面试 / 表达方法`（546）、`表达与答题框架`（555） vs `通用表达方法`（543） | 删 546、555（都是空节点），保留 543 |
| `Redis / 分布式锁`（145） vs `分布式与微服务 / 分布式锁`（545） | 都留，但把边界写死：145 放「Redis 实现：SETNX+PX、看门狗续期、RedLock 争议」，545 放「通用方案与选型：zk 临时顺序节点、etcd 租约、DB 行锁；不放 Redis 实现细节」 |

清理后：219 个节点、6 个根、0 个孤儿、0 条重复挂载。
「Redis 看门狗」那题的 4 个切片仍然 4/4 落在 `redis/分布式锁`。

## 7. 附带修掉的：带代码块的文档传不上去

上传 `2026-08-20-用友-电话初筛未通过.md`（6.8 KB，7 个代码块）后状态直接是「失败」，错误
`document block text is required`，切片 0。

原因在 Markdown 解析器：它把每一行都当正文处理，闭合围栏那行是三个反引号，而
`cleanMarkdown` 会把反引号洗掉，洗完成空串；`DocumentBlock` 又不接受空文本，于是一行
` ``` ` 把整篇文档炸掉。同一批的 `萤火虫` 那篇 0 个代码块，所以没事。

修了三处：

| 问题 | 处理 |
|---|---|
| 围栏行被当正文 | 围栏只作状态切换（进出代码块），本身不入块 |
| 代码块内容被洗 | 块内行原样保留，`*` `_` `` ` `` 不再被删 |
| 分隔线进切片 | `---` / `===` / `***` 直接跳过；洗成空串的行也跳过 |

### 7.1 但能传上去只是第一步

能解析不等于能用。接着查切片正文，发现三处更伤的问题：

**① 缩进全没了。** 解析时每行都 `strip()`，Python 的缩进是语法的一部分：

```python
class AgentOutput(BaseModel):
    thought: str          ← 缩进被吃掉，变成 thought: str 顶格
    action: Literal["tool_call", "finish"]
```

现在围栏内只去行尾空白、保留左缩进。

**② 一段代码会被切成两片。** 切片器按 token 数和字符数切，正好从一个 f-string 中间劈开：

```
切片 4 结尾：任务：{task_description}
切片 5 开头：历史：{format_history(history)}
```

现在新增 `DocumentBlockType.CODE`：一个围栏里的一段代码就是一个原子块，切片器不许从中间切；
真的超长时按换行边界切，每一刀都落在行首。

**③ 技术名词被 markdown 清洗毁掉。** 原来是 `replaceAll("[`*_]", "")`，无差别删字符：

```
idx_name_age  →  idxnameage      （索引名糊了，检索也找不到）
__init__      →  init
SELECT * FROM →  SELECT  FROM
```

改成只去真的装饰语法：`**粗体**`、`__粗体__`、`*斜体*`、`` `行内代码` `` 仍然去掉，
但标识符里的下划线、SQL 里的 `*` 都留着。

落地时切片正文再补回围栏，前端按 markdown 渲染（深色 `<pre>` + 等宽），复制出去仍是能跑的代码。

| 校验项 | 结果 |
|---|---|
| 27 篇笔记解析 | 3207 块，0 失败 |
| `idx_name_age` 保留 / 被洗坏 | 2 处 / 0 处 |
| 后端测试 | 122 个全过 |

### 7.2 切片不许切进代码块

一个围栏里的一段代码 = 一个 `DocumentBlockType.CODE` 块，切片器把它当原子单元：

- 进切片时整块放入，不够放就先 flush 当前片，另起一片
- 真的超过单片上限时，只在换行处断开，每刀落在行首
- 正文里的代码行不会被当成"题目起点"（`isQuestion` 判断跳过 CODE 块）

校验：88 个带围栏的切片，**围栏数为零的奇数个** —— 也就是说没有任何一片只含半个代码块。

| 校验项 | 结果 |
|---|---|
| 带围栏的切片 | 88 |
| 其中围栏不成对（被切断） | 0 |

### 7.3 题目答案也要带代码

切片修好只解决一半：题目是另一条链路。`plainText()` 把块拼成纯文本喂给抽题器，
原来代码块不带围栏、块之间也没有空行，导致

- 抽出的答案里代码是一堆没有边界的行，前端整段塌成文字（652 道题只有 80 道带代码）
- 抽题器只能靠"像不像疑问句"判边界，「5. Java 数组常用方法」这种陈述式题号被漏掉，
  上一题的答案一路吞下去：「MyBatis 中 # 和 $ 的区别」的答案从 275 字符涨到 1554 字符，
  吞进了 AOP、数组、List 三节内容

改法：

1. `plainText()` 里 TITLE 保留 `##` 前缀、CODE 补回围栏、块之间空一行
2. 有"像题目的标题"时只认标题（`## 3. xxx`）；没有才退回编号行，且要求题号连续、行前有空行
3. 标题判断比正文严：问号结尾或以「如何/为什么/谈谈/介绍/讲解…」开头，
   避免「### 实现思路」被当题目

效果：652 道题，答案最长 2256 字符，平均 257，没有一道超 3000（串题的标志）。

| 校验项 | 结果 |
|---|---|
| 题目数 | 652（原 532，早先漏识别了一批陈述式题目） |
| 答案带代码块 | 80 道 |
| 答案超 3000 字符（串题） | 0 道 |

顺带发现切片归类的两个系统性问题，一并修了：

**切片标题缺上下文**。「简短回答」「详细解析」这种标题对归类零信息量，模型会把
「MyBatis 中 # 和 $ 的区别」下面的「简短回答」挂到「Agent / 工具调用 / 工具定义与参数校验」。
现在标题拼上所属题目：`4. MyBatis 中 # 和 $ 的区别 · 简短回答`，锚词能命中，模型也有依据。

**批边界切断兄弟关系**。一篇文档的第 20 个切片要不要跟着第 19 个走，取决于 19 落在哪，
但 10 条的批边界常把它们劈开。现在维护一张「章节 → 主题」表跨批记忆，同章节的后续切片直接继承。
（试过把定主题的整批扩到 47 条，模型质量明显下降，所以仍是 10 条一批，靠这张表兜底。）

修完这份文档 23 个切片：22 个挂上、全部落在正确主题，1 个是文档标题本身（不挂是对的）。

随后把用户 Obsidian 里的 27 篇面试笔记整批导入，作为真实回归：

```
27 篇（21 篇带代码块，最多一篇 40 行围栏 / 20 个代码块）
990 个切片       全部 READY，0 个失败
532 道题         582 条挂载（579 待确认 + 3 人工确认），205 条留空等人看
```

同一批文件在修之前，凡是带代码块的都会停在「失败 / 切片 0」。

整批导入还暴露了一个准确率问题：低置信（0.72~0.78）的题会挤进同一个叶子。
「断点续传」下曾挂着「如何跟进大模型与 Agent 进展」「如何设计 Agent 沙箱」这种题——
因为 Agent 类锚词当时一个都没有，模型在 181 个叶子里随手挑了个"看着技术"的。
补上 Agent / 网络 / 分布式三组锚词后，这 6 条全部转为留空，该叶子下只剩真的讲断点续传的题。

## 10. 文档级类型闸门（2026-11-13 补）

上一节所有手段都在回答"这条内容归哪个目录"，但库里还有更前面的一层漏了：
**"这份文档该不该被切成题"**。`KbKind` 是知识库级的，题库库里所有文档都进
`KbQuestionParser`，而解析器兜底是"只要有正文就出一题"，于是：

| 文档 | 抽出 | 实际是 |
|---|---|---|
| `README.md` | 6 题（面试题目 / 简短回答 / 详细解析 / 常见追问 / 回答要点 / 关联知识，答案全 NULL） | 模板说明 |
| `黄洋_Java后端面试准备.md` | 31 题（`1 一分钟版`、`3 技术深挖`、`1 所有数字都要能交代"怎么测的"`） | 口播稿 + 答题要点 |
| `HashMap扩容与树化专项总结.md` | 7 题（`为什么需要扩容？`…） | 一篇讲义 |

这些"题"再被归类器挂到 `面试 / 通用表达方法`（置信度 0.90~0.95），就成了
"知识点被放进了面试题里"。**描述不是原因**：库 1 的 220 个节点 description 全为非空
（库 2「技术知识」才是 209/214 为空，该补的是那边）。

### 10.1 判定方式

`KbDocumentKindGate`，先规则打分（题库倾向，可正可负），每项都写进 `evidence`：

| 信号 | 权重 |
|---|---|
| 文件名含 面经 / 面试题 / 真题 / 八股 / 题库 | +0.15 |
| 题面像问题（问号结尾或以 如何/为什么/… 开头）≥60% | +0.25（≥35% 给 +0.12） |
| 题号连续段 ≥3 | +0.25 |
| 平均答案长度 80–800 字 | +0.10（<40 字 −0.20） |
| 有「答案：/解析：/参考答案」 | +0.15 |
| 面试语境词 ≥3 处（面试/一面/笔试/候选人…） | +0.15 |
| 章级结构 ≥2 处（一、二、… / 第 N 章） | −0.15 |
| 模板字段 ≥4 个（简短回答/详细解析/口播版/技术深挖…） | −0.25 |
| 伪题率 ≥30%（题干是小节目录名） | −0.30 |
| 文件名含 总结 / 专项 / 笔记 / 清单 / 准备 / README | −0.30 |

- ≥0.55 判题库；<0.40 判知识点；中间那段**问一次模型**（一篇文档一次调用）；
  模型不可用时**保守判题库**——少抽一道能重跑，误删一批是事故。
- 口径修正：模板字段初版按"出现 2 次"扣 0.35，实测把 5 份真题面经一起误杀
  （面经里本来就有「回答要点」小节），改成"≥4 个字段才扣 0.25"。

### 10.2 真实 27 篇回测

| 文档 | 分数 | 判定 |
|---|---|---|
