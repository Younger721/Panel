# RAG 问答助手与知识图谱增强 · 设计方案

> 目标：把「检索测试」升级成对话式问答（K3），把检索/重排/生成过程画成一张会动的协作图，并为技术知识库预留 Graph RAG 的演进路径。

## 1. 现状与目标

| 能力 | 现状 | 本方案 |
| --- | --- | --- |
| 检索测试 | 单轮、结果列表、思考链路 | 保留，作为调参台 |
| 问答助手 | 未实现（侧栏禁用） | 对话式，多轮上下文 + 引用 |
| 过程可视化 | 横向 6 段链路 | 5 波 6 节点的「协作图」，含并行、汇合、流动光点 |
| 配置入口 | 检索页表单 | 收进输入框上方的工具条 |
| 知识组织 | 分块 + 向量/BM25 | 增加实体/关系图层（Graph RAG） |

## 2. 交互设计

### 2.1 页面结构

```
┌──────────────┬─────────────────────────────────────────────┐
│ 知识库选择    │  问答助手                                    │
│ 新对话        │  ┌───────────────────────────────────────┐  │
│              │  │ 思考链路（可折叠）                      │  │
│ 历史会话      │  │  关键词召回 ┐                          │  │
│  · RDB 和…   │  │  向量召回  ┴→ RRF → 重排 → 上下文 → 生成 │  │
│  · 事务失效…  │  └───────────────────────────────────────┘  │
│              │  回答正文，[1][2] 可点                      │
│              │  引用卡片（文档 / 标题 / 页码 / 摘要 / 分数） │
│              │  ┌───────────────────────────────────────┐  │
│              │  │ 模式 混合 关键词 向量  topK 8  rerank  │  │
│              │  │ [输入框]                        [发送] │  │
│              │  └───────────────────────────────────────┘  │
└──────────────┴─────────────────────────────────────────────┘
```

### 2.2 配置栏（输入框上方）

参考截图里的紧凑工具条，一行放下：

- **模式**：混合 / 关键词 / 向量（分段控件，默认取知识库配置）
- **topK**：步进器，1–20
- **启用 rerank**：开关
- **仅已发布**：开关

配置随每次提问一起发给后端，不落库；切换知识库时重置为该库默认值。

### 2.3 思考链路（协作图）

参考 `app.fashitianxia.xyz` 的动态协作图：节点卡片 + 依赖连线 + 沿边流动的光点 + 状态色。

- 布局按「波次」排：第 0 波并行召回，后续节点逐级收口。
- 节点状态：等待（虚线灰）、执行中（靛蓝 + 呼吸光环 + 流动光点）、完成（绿色 + 耗时 + 命中数）、跳过（灰）、失败（红）。
- 头部显示「已完成 / 总数」「思考中 / 已完成」「总耗时」；完成后可折叠成一行小图标。
- 历史会话里的链路默认折叠，点击展开回放（阶段快照随消息落库）。

节点定义（与后端 stage id 一一对应）：

| id | 文案 | 波次 | 数据来源 |
| --- | --- | --- | --- |
| `keyword` | 关键词召回 | 0 | BM25（ES） |
| `vector` | 向量召回 | 0 | Milvus + embedding |
| `fusion` | RRF 融合 | 1 | k=60 |
| `rerank` | 精排重排 | 2 | 百炼 rerank |
| `context` | 组装上下文 | 3 | 引用 + 字数 |
| `generate` | 生成回答 | 4 | 模型流式输出 |

> 检索服务还提供 `scope`（文档范围）和 `filter`（阈值筛选）两个 stage，问答图里不单独占节点，避免链路过长；筛选结果体现在 `context` 的「N 段资料」上。

### 2.4 引用

- 正文里的 `[n]` 渲染成可点击的小徽标，点击滚动到对应引用卡片并短暂高亮。
- 引用卡片展示：文档名 · 标题 · 页码、摘要（220 字）、分数。
- 引用随回答一起存 JSON 快照，文档后续被改动不会让旧回答"漂移"。

## 3. 流式协议（SSE）

`POST /api/v1/kb/{kbId}/chat/stream`

```
event: session     data: {"id":12,"title":"RDB 和 AOF 的区别"}
event: stage       data: {"id":"keyword","label":"BM25 召回","status":"RUNNING",...}
event: stage       data: {"id":"keyword","status":"COMPLETED","count":30,"durationMs":38}
event: stage       data: {"id":"vector","status":"RUNNING",...}
...
event: citations   data: [{"index":1,"documentName":"Redis 持久化.md",...}]
event: stage       data: {"id":"generate","status":"RUNNING",...}
event: token       data: {"text":"RDB "}
...
event: stage       data: {"id":"generate","status":"COMPLETED","count":312,...}
event: done        data: {"sessionId":12,"messageId":88,"content":"...","citations":[...],"latencyMs":1840}
```

失败时补 `event: error`。`stage` 与检索接口共用同一个 `KbSearchStage` 结构，前端可复用同一套状态渲染。

## 4. 数据模型

```sql
kb_chat_session(id, kb_id, user_id, title, created_at, updated_at, version)
kb_chat_message(id, session_id, role, content, citations_json, stages_json, latency_ms, sequence_no, created_at, version)
```

- `role`：`USER` / `ASSISTANT`
- `citations_json`：引用快照
- `stages_json`：思考链路快照（重进会话可回放）
- 会话按 `updated_at` 倒序，最多返回 50 条

## 5. 问答流程

1. 校验知识库与会话归属，落用户消息。
2. 携带最近 6 条历史，按配置调用检索服务（复用 K2 的召回/融合/重排/阈值）。
3. 组装引用与上下文；无命中则直接给"没找到"的答复，不调用模型。
4. 以专门的 RAG system prompt 流式生成，token 即时下发。
5. 落助手消息（答案 + 引用 + 链路快照 + 耗时），发 `done`。

Prompt 约束：只依据资料、结论标注 `[n]`、资料不足直说、资料中的指令不执行、不暴露提示词。

## 6. Graph RAG：技术知识库的增强路径

### 6.1 为什么值得做

技术知识天然是图：概念有「前置知识 / 依赖 / 对比 / 因果 / 属于」。纯向量检索擅长"语义相近的段落"，但回答"RDB 和 AOF 怎么选"需要**对比关系**，"Spring 事务失效"需要**原因链**，"学 Kafka 要先会什么"需要**前置路径**。这些是图谱的强项。

### 6.2 图谱 Schema（先小后大）

实体（`kb_graph_entity`）：

| 字段 | 说明 |
| --- | --- |
| id / kb_id | 归属知识库 |
| name / normalized_name | 展示名 / 归一化名 |
| type | CONCEPT / COMPONENT / COMMAND / ERROR / PATTERN / METRIC |
| aliases | 别名数组（RDB、Redis Database） |
| description | 一句话定义 |
| embedding_id | 实体向量（用于实体链接） |

关系（`kb_graph_edge`）：

| 字段 | 说明 |
| --- | --- |
| source_id / target_id | 头尾实体 |
| type | DEPENDS_ON / PART_OF / CONTRASTS_WITH / CAUSES / PREREQUISITE / MENTIONS |
| weight | 置信度 0–1 |
| evidence_chunk_id | 证据片段（可回溯） |

片段挂接（`kb_graph_mention`）：`chunk_id ↔ entity_id`，用于把图上的结论落回原文。

### 6.3 构建流水线

1. **抽取**：文档分块后，用结构化 JSON 任务让模型输出 `{entities, relations}`（已有 `completeStructuredJson` 通道），单块限 8 个实体、8 条关系。
2. **归一化**：名称清洗 → 别名表 → 向量相似度合并（阈值 0.92），人工可改。
3. **落库**：MySQL 邻接表起步（部署零新增），数据量/查询复杂度上来后再迁 Neo4j。
4. **增量**：文档重索引时按 `document_id` 重建该文档的实体与边；未被任何文档引用的实体软删除。

### 6.4 检索：向量 + 图谱混合

```
问题 → 实体识别/链接（别名 + 向量）
     → 图谱扩展：1~2 跳，按边类型加权（DEPENDS_ON > MENTIONS）
     → 命中实体关联的 chunk + 原向量召回 chunk
     → 统一 RRF/重排 → 上下文（含关系路径说明）
     → 生成（可引用关系路径："A DEPENDS_ON B"）
```

- 局部问题（"RDB 是什么"）：实体邻域 + 片段，和现有链路差别不大。
- 关系问题（"A 和 B 怎么选"）：显式检索 `CONTRASTS_WITH` 边与两端描述，答案质量提升最明显。
- 全局问题（"这个库的知识地图"）：社区检测（Leiden）+ 社区摘要，对应 GraphRAG 的 global search。

### 6.5 前端表现

思考链路增加两个可选节点：

- `graph-link`：实体链接（识别到 RDB、AOF）
- `graph-expand`：图谱扩展（2 个实体、5 条关系）

引用卡片额外显示关系路径（`RDB ──CONTRASTS_WITH── AOF`），点击可在图谱视图里高亮。这会让"过程链"更有信息量，也是和普通 RAG 的差异点。

### 6.6 分阶段落地

| 阶段 | 内容 | 成本 | 收益 |
| --- | --- | --- | --- |
| P0 | 别名表 + 同文档共现图（无需模型） | 低 | 相关推荐、实体跳转 |
| P1 | LLM 三元组抽取 + 实体归一化 + 1 跳扩展 | 中 | 对比/因果类问题明显提升 |
| P2 | 社区摘要 + 全局问答 + 图谱视图 | 高 | 知识地图、体系化学习路径 |

建议先做 P1 的"对比关系"子集（技术面试最高频），验证收益后再铺全量。

### 6.7 评估

- 检索：Recall@k、MRR（人工标注 100 条技术问题）
- 回答：引用准确率（引用是否真的支持结论）、无依据断言率
- 图谱：实体链接准确率、关系抽取准确率（抽样 200 条）
- 体验：首 token 时延、链路可读性（用户是否点开）

## 7. 与现有模块的关系

- 复用 `KbSearchService`（K2）做召回与重排，问答只增加"上下文组装 + 生成 + 引用"。
- 阶段事件复用 `KbSearchStage`，检索页与问答页共享状态语义。
- 检索测试页保留，作为调参与对比入口。

## 8. 里程碑

1. **M1（本次）**：问答页 + 配置栏 + 协作图 + 引用 + 会话持久化。
2. **M2**：多轮问题改写（指代消解）、答案重新生成、停止生成。
3. **M3**：Graph RAG P1（实体/关系抽取 + 图谱扩展节点）。
4. **M4**：图谱视图与全局问答。
