# 刷题与知识点联动（实现说明）

> 目标：上传题库文档 → 随机抽一组题（默认 5）→ **只看题面** → 自己想完再展开答案 → 自评对错 → 答错立刻看到对应知识点，并能跳到目录里继续翻。

设计上刻意**没有**做实体级知识图谱（`kb_concept` / `kb_graph_edge` 保持关闭）。理由是：题目和知识点的对应关系已经存在于 `kb_item_category`（题 → 目录节点），而目录本身就是一棵 3 层的树；再加一层概念图，收益是"猜测关联"，成本是抽取、维护、错链。真正缺的不是图，是**树的结构对齐**和**覆盖率**。

## 1. 数据模型

`backend/src/main/resources/db/migration/V8__kb_quiz.sql`

| 表 | 作用 | 关键点 |
|---|---|---|
| `kb_quiz_session` | 一组题（一次"开一组"） | `status` RUNNING/FINISHED、`question_count/correct_count/wrong_count` |
| `kb_quiz_attempt` | 一组里的每一题 | `uk_kb_quiz_attempt_slot(session_id, ordinal)` 保证不重复占位；`result` 为 CORRECT/WRONG/UNSURE/SKIPPED；`category_id` 是**抽题当时的**知识点快照 |
| `kb_category_relation` | 知识点之间的轻量横向关系 | `relation` RELATED/PREREQUISITE/CONTRAST + `weight`；三元组唯一，重复创建走 upsert |

`kb_quiz_attempt.category_id` 存快照而不是每次 join `kb_item_category`，这样以后重新分类不会把历史记录改写成"另一道题"。

### 2.1 抽题算法

1. **分桶**：按主知识点分桶；
2. **抽桶（加权）**：桶权重 = 桶内未抽走的题里最弱的那道题的权重。抽中一个桶只给 1 个名额 ——
   既保证 5 题不砸在同一个节点，又让弱节点被选中的概率更高；
3. **单题权重**：有能力值就按 `0.3 + 3.0 × wrongRate^1.5`（越弱越高），再乘近期因子
   （近 3 天错过 ×1.5、近 3 天做对 ×0.25、更早做对 ×0.8）；能力值表为空 / 开关关掉时退回旧的固定启发式
   （错 ×3.0、没做 ×1.2、近对 ×0.25、旧对 ×0.8）；
4. **补名额**：桶数少于题数时，第二轮继续给有余量的桶加权补名额，每桶上限 `MAX_PER_NODE=2`；
5. **兜底**：还不够就从剩余池继续抽，直到凑够 `size` 或题库见底，最后整体打乱。

> 关键一点：**桶的优先级必须加权**，不能"先打乱桶再轮流取"。轮流取的话，能力值只影响同一个桶内部的取题顺序，
> 影响不了"哪些知识点出现在这一组里"，弱项加权形同虚设 —— 这一点是第一版实现踩过的坑（见 §5 第六轮）。

`latest` 只认**已作答**的记录：抽题会先落一条未作答的 `kb_quiz_attempt`，如果把它当成"最近一次"，
打开一组题不作答就会把历史信号抹掉。

开关：`panel.kb.quiz.skill-weight`（默认 `true`，环境变量 `PANEL_KB_QUIZ_SKILL_WEIGHT`），关掉退回旧启发式，用于 A/B。

这套逻辑是 `KbQuizService.sample(...)`，输入只有 id 集合 + 分类映射 + 最近作答映射 + 能力值映射，
所以可以脱离数据库直接单测（`KbQuizSamplingTest` 4 例、`KbQuizWeightTest` 4 例）。

### 2.2 答案不下发

`POST /quiz` 和 `GET /quiz/sessions/{id}` 返回的 `items` 只有 `stem/difficulty/tags`，**没有 `answer`**；答案只在 `POST /quiz/attempts/{id}/reveal` 里返回，同时记录 `revealed_at`，用来算"看题到看答案"的思考秒数（太短说明没在回忆）。

### 2.3 能力值模型（`kb_skill_state`）

口径：一个知识点一个能力值 `theta`，一道题一个难度 `b`，`P(答对) = 1 / (1 + exp(-(theta - b)))`，
观测到结果后 `theta += weight × K × (observed - P)`。

| 参数 | 值 | 理由 |
|---|---|---|
| `K0` | 0.6 | 初始学习率 |
| `K` | `K0 / (1 + 0.15 × attempts)` | 做得越多单次冲击越小，一两题翻不了盘 |
| 难度 `b` | `1~5 星 → -2.4~2.4`；"难/HARD"=1.2、"中"=0、"易"=-1.2，认不出来按 0 | `kb_question.difficulty` 是自由文本，必须容错 |
| 观测值 | CORRECT=1、WRONG=0、UNSURE=0.5 | "不确定"有信息但不算对 |
| 权重 | 面试 ×2、UNSURE ×0.5 | 面试是高压真实场景，信号更硬 |
| 遗忘 | `theta × max(0.6, exp(-天数/30))` | 久不练向 0 回落，但最多回落 40%，不抹平已证明的强项 |
| 聚合 | 父节点 = 子节点按 `attempts` 加权平均 | 树才给得出的"整块弱"：TCP 弱 → 计算机网络弱 |

对外只暴露一个可解释数字：`wrongRate = 1 - P(答对)`，"下次抽到中等难度的题，你答错的概率"。

写入点两个：`KbQuizService.grade()`（刷题自评）与 `KbSkillService.record(..., interview=true)`
（面试，入口见 §2.5 回填）。
读取点两个：`GET /{kbId}/quiz/skills`（面板展示：`points` 叶子 + `branches` 父节点聚合）
与 `KbSkillService.effectiveThetas(...)`（抽题时算权重，见 §2.1）。

- 能力值按 **知识点** 记账，不跟题目走：把一道题从 A 节点挪到 B 节点，历史能力值留在 A，下一次作答才记到 B。
- 没作答过的知识点没有记录，不会出现在 `skills.points` 里（用先验补全还没做）。

### 2.4 面试信号回填（`kb_skill_interview_import`）

能力值表是新的，而面试记录已经攒了几十轮。不回填的话，"面试弱但刷题还行"永远判断不出来——
因为面试那一半信号根本没进账。

**折算口径**：`interview_turn.skill`（自由文本，如"自我介绍""技术栈堆叠无深度标注"）
按名字对齐到目标库的知识点，`final_score`（0~100）折算成观测：

| 得分 | 观测 | 说明 |
|---|---|---|
| ≥ 70 | `CORRECT` | 这轮答得算过 |
| 40 ~ 69 | `UNSURE` | 半对，有信息但不加分 |
| < 40 | `WRONG` | 明确没答好 |

写库时 `interview=true`，所以权重 ×2、`interview_count` 累加、`last_source=INTERVIEW`。

**名字对齐的规则**（`InterviewSkillMatcher`）：归一化（去空白/标点、统一全半角与大小写）后
完全相同 → 命中；否则互相包含取**最长的节点名** → 命中；都不行 → 返回 null。
刻意不做模糊匹配、不调模型：目录是产品结构，**错挂比不挂更糟**（答错时知识点会指错，学员会以为系统在胡说）。

**三个约束**：

1. **幂等**：每条 turn 折算后写进 `kb_skill_interview_import`（`turn_id` 唯一）。重复调用只处理新增轮次，
   也能顺着台账查"我这个知识点为什么是 -1.9"。
2. **不让模型造节点**：匹配不到就报出来（`unmatchedSamples`）；要建节点必须显式 `createMissing=true`，
   统一挂在 `rootName`（默认「面试评估」）下面，便于整体删改。
3. **先干跑**：`dryRun=true`（默认）只返回"会匹配到哪、多少条匹配不上"，不写库。

**谁的能力值**：`interview_session` 只挂在 `resume` 上，而 `resume` 没有 `user_id`，
所以 `interview_turn` 无法自动归属到人——接口必须显式给 `userId`（默认取当前操作人）。
这是已知缺口，见 §4。

### 2.5 按文档一键归类

覆盖率看板按文档列出缺口（`未挂 N` / `待确认 N`），每个文档后面有「一键归类」按钮，
走 `POST /{kbId}/catalog/documents/{documentId}/classify`：

- **只碰这份文档**：题目按 `document_id` 取（题库），技术文档按 chunk 取（没有题目时才用切片），
  已经挂过的不动；
- **`redoLowConfidence=true`**：先把这份文档里"未锁定 且 置信度 < 0.72"的挂载删掉再重跑。
  低置信建议本来就是模型没把握的结果，不给它重来的机会，看板上的「待确认」只能靠人工一条条点；
  人工确认过的（`locked=true`、置信度 1.0）一律不动——这是全系统唯一的"人工真值"通道；
- 返回 `{llmApplied, ruleApplied, skipped, mode, cleared}`，UI 直接把这条写成一句人话：
  `归类 1 条 · 清掉低置信 1 条 · 仍有 3 条没把握 · 模式 LLM`。

阈值与实现：`KbAutoClassifyService.AUTO_APPLY=0.72`；LLM 优先（每批 10 条，`categoryId` 命中已有节点，
否则给 `path` 现建），LLM 不可用或没命中就退回关键词规则（节点名整串出现 0.82、`pathKey` 尾段命中 0.74）。

### 2.6 可见性（`kb_base.visibility`）

规则：`PUBLIC` 谁都能读；`INTERNAL` 只对 `PLATFORM_ADMIN` / `ADMIN` / `INTERVIEWER` 开放。

- 列表：`GET /api/v1/kb` 用 `guard.canRead` **过滤**，候选人看不到 INTERNAL 的库（连 id 都不知道）；
- 单点：`KnowledgeBaseService.get`、`KbDocumentService`（上传/列表）、`KbCatalogService`（树/条目/挂载/覆盖率）、`KbQuizService`（抽题/统计/错题本/能力值）、`KbSearchService`（检索）、`KbChatService`（会话）全部走 `guard.ensureReadable`，直连 id 也是 403。

验证（dev，租户 demo1 的 CANDIDATE 账号）：`GET /kb` 只返回 `tech-knowledge`、`job-knowledge` 两个 PUBLIC 库；`/kb/6/catalog/tree`、`/kb/6/quiz/stats`、`/kb/6/quiz/skills`、`/kb/1/documents`、`/kb/7/catalog/coverage`、`/kb/6` 全部 403；`/kb/2`、`/kb/2/documents` 正常 200。

注意 `skills` 只要求"库可读"，**不要求是题库**：面试信号会落在"岗位与公司""技术知识"这类库的知识点上，
能力值本来就是跨库概念，只有抽题必须落在题库上。

## 3. 前端

- 路由 `/kb/quiz`（导航"知识库管理 → 刷题"），页面 `frontend/src/pages/KbQuizPage.tsx`，API `frontend/src/api/quiz.ts`。
- 交互：题面 → `我答完了，看答案` → 答案 + `答对了 / 答错了 / 不确定` → 答错/不确定时展示知识点卡片 + 相关知识点 + `去知识点目录看`。
- 右侧常驻：**能力值**（按"下次答错概率"排，带样本量提示，父节点显示"整块弱"）、薄弱知识点（按错题数）、错题本；顶部 4 个指标 + 覆盖率告警条，告警条下面是可展开的「目录体检」队列（逐条 `确认归属` / `改挂` / `去挂一个`）。
- 「目录体检」里的「按文档看缺口」每行带一个 `一键归类` 按钮：有「待确认」时按重跑口径（先清低置信）执行，否则只补未挂的；执行完提示一行结果并自动刷新看板。
- 目录页 `/kb/:id/catalog` 对题库库多一个「继承目录…」下拉：选另一个库就能把它的 `kb_category` 树按 `path_key` 复制过来。
- 目录页还有「面试信号回填」按钮：先干跑（提示"待折算 N 轮 / 需要新建 M 个知识点"），确认后点「应用回填」才写库；
  应用后目录树自动刷新，`面试评估` 节点下就能看到新建出来的叶子。
- 深链：`/kb/:id/catalog?node=<categoryId>` 会直接选中该节点（`KbCatalogPage` 读取 `node` 参数），刷题页所有知识点链接都用这个格式。
- 答案不提前泄露：`/api/v1/kb/{kbId}/questions` 列表**不返回 answer**，题库浏览页选中某题后才调 `/api/v1/kb/questions/{id}` 拉详情。

## 4. 已知边界（按优先级）

1. **两棵目录树语义仍未统一**：题库库（`question-bank`）和技术知识库（`tech-knowledge`）各有自己的 `kb_category` 树。现在可以用 `POST /catalog/import?sourceKbId=` 把技术知识库的树按 `path_key` 继承到题库库（幂等、只补不改），但**两棵树的节点仍然各自维护**：改了一边不会同步另一边。彻底解法是单树多视图，或者树节点带 `shared_key` 走同一张表。
2. **相关知识点是手工/待生成的**：`kb_category_relation` 目前只有 CRUD，没有自动生成（可以后续用 LLM 生成候选、人工确认，`source=AI`）。
3. **覆盖率决定体验**：自动分类阈值 0.72。`/catalog/coverage` 的 `gaps` 把「低置信」和「未挂知识点」两类缺口列出来（各最多 20 条），刷题页的「目录体检」支持单条确认、`全部确认（N 条）`批量确认、按文档一键归类，以及按文档聚合的缺口（`documents[]`，显示每份文档已挂/未挂/待确认）。剩下的缺口是"分类器确实不会"的那批（题目里没有任何目录词），只能人工挂或补目录。
4. **"正确率"口径**：`accuracy = 对 / 已作答`，选了「不确定」算进分母、不算错；错题本把 UNSURE 也算错题，因为"没答对"就该复习。
5. **能力值已经接管抽题，但只是"倾斜"不是"垄断"**：`0.3 + 3.0 × wrongRate^1.5` 乘近期因子之后，最弱项与最强项的权重比大约 3~4 倍；桶上限 `MAX_PER_NODE=2` 保证不会 5 题全砸在一个弱节点。要更激进就调 `THETA_SPAN` / `THETA_POWER`。
6. **面试信号归属靠人给**：`interview_turn` 挂在 `interview_session` → `resume`，而 `resume` **没有 `user_id`**，
   所以回填必须显式指定 `userId`（默认取当前操作人）。多租户/多候选人场景要先给简历加归属列，否则评分会记到错的账上。
7. **面试 skill 只能"名字对齐"**：`InterviewSkillMatcher` 不做模糊匹配，所以第一次回填常常是"0 命中 + 一堆待建节点"。
   这是刻意的：目录是产品结构，错挂比不挂更糟。要提命中率，正确的是把面试评分 prompt 的 skill 枚举约束到已有节点，
   而不是让匹配器去猜。
8. **能力值只看「刷过的那几个节点」**：没作答过的知识点没有记录，也不会出现在 `/quiz/skills` 里。要么用先验（该节点题目难度中位数）补出来，要么在 UI 上明确"没做过不等于不会"。
9. **外部索引后端（ES 9202 / Milvus 19530）是可选依赖**：没起来时不再让整条链路报错（原来上传会 FAILED、删文档直接 500「服务器内部错误」）。
   现在 `KbIndexer` 探测失败后进入 30 秒冷却窗，判断为"只落库、不写外部索引"，文档照常进 `READY`，
   `index_generation` 记为 `local-<docId>-<ts>`；删除/重索引也照常成功。
   代价是**检索测试不可用**（两路召回都靠外部后端），会返回 503 并说明原因，不再是一句"服务器内部错误"。
   回归用例：`KbIndexerDegradeTest`（后端不可用时删除不抛异常、索引返回降级 generation）。
