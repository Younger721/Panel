# 部署与升级运行手册（生产）

> 适用：Spring Boot 3.4.12（Java 21）+ React/Vite 前端 + MySQL 8 + Redis 7，单机起步。
> 配套：[上线方案-注册与数据隔离](上线方案-注册与数据隔离.md)、[部署计划-生产上线](部署计划-生产上线.md)（本手册是它的"可运维版"，补了多用户上线必须的容量、蓝绿与回滚）。

---

## 1. 目标架构

### 1.1 起步形态（0–500 用户，4C4G 单机）

```
                     ┌──────────── Nginx (80/443) ────────────┐
浏览器 ──HTTPS──────>│  /            → /var/www/panel/current  │
                     │  /api/        → upstream panel_backend  │
                     │  /ws/         → same upstream (Upgrade) │
                     └───────────────┬─────────────────────────┘
                                     │ 127.0.0.1:8080 (blue) / 8081 (green)
                             Spring Boot（systemd 模板实例）
                                     ├── MySQL 8     127.0.0.1:3306
                                     ├── Redis 7     127.0.0.1:6379
                                     ├── 本地对象存储 /opt/panel/data/knowledge
                                     └── 百炼 API（出网）
```

为什么不用 Docker 起步：4G 内存里编排层本身吃掉 200–300M，而蓝绿发布用 systemd 模板实例（`panel-backend@blue` / `@green`）同样能做到原子切换，还少一层网络与卷的坑。`deploy/docker-compose.prod.yml` 留给"换机器 / 扩容 / 迁移到托管中间件"时用。

### 1.2 扩容路径

| 触发条件 | 动作 | 影响 |
|---|---|---|
| 内存常驻 > 3.2G / 频繁 Full GC | 升 8G；或把 MySQL 换云托管 CDB | 改 `.env` 的 `MYSQL_HOST` 即可 |
| 检索变慢、重启后重建索引太久 | 装 ES + Qdrant（或 ES dense_vector），`PANEL_SEARCH_*_BACKEND` 切回 | 需重新建索引 |
| 单机故障不可接受 | 后端 2 实例 + Nginx 双 upstream + 云 MySQL/Redis | 无状态，直接加实例 |
| 前端要 CDN | `dist` 传 COS + CDN，`/api` 回源 | 无需改构建 |

### 1.3 容量基线（实测口径要自己压）

| 项 | 数值 | 说明 |
|---|---|---|
| JVM | `-Xms768m -Xmx1280m` | G1，4G 机器别超过 1.5G |
| MySQL | `innodb_buffer_pool_size=256M` | 数据量 < 2G 时够 |
| Redis | `maxmemory 256mb`，`noeviction` | 会话 + 限流计数，丢了只影响登录态 |
| 并发 SSE | Tomcat `threads.max=200`（默认） | **每条 SSE 占一个线程**，200 是硬上限 |
| 估算承载 | 30–50 并发在线、200–500 DAU | 瓶颈在模型延迟，不在应用 |

> SSE 与 ASR WebSocket 都是长连接。做发布时不要指望"无缝"：老实例上的面试会断。所以发布安排在低峰，并接受"正在进行中的面试会中断"。

## 2. 环境与变量

### 2.1 目录布局

```
/opt/panel/
├── releases/
│   ├── 20261113-a1b2c3d/panel-backend.jar
│   └── 20261120-e4f5g6h/panel-backend.jar
├── current -> releases/20261120-e4f5g6h        # 原子切换，回滚就是改软链
├── data/knowledge/                              # 本地对象存储
├── backup/                                      # 每日备份
└── logs/backend.log                             # 或直接 journald

/var/www/panel/
├── releases/<ver>/                              # dist 内容
└── current -> releases/<ver>

/etc/panel/
├── panel.env                                    # 所有实例共用（密钥、中间件、模型）
├── blue.env                                     # SERVER_PORT=8080
└── green.env                                    # SERVER_PORT=8081

/etc/nginx/
├── panel-upstream.conf                          # 由切换脚本重写，只含 upstream 指向
└── sites-available/panel
```

### 2.2 必需变量（完整模板见 `deploy/env/panel.env.example`）

```properties
# --- 库 ---
MYSQL_HOST=127.0.0.1
MYSQL_PORT=3306
MYSQL_DATABASE=panel_ai
MYSQL_USER=panel
MYSQL_PASSWORD=<强密码>

# --- 缓存/会话 ---
REDIS_HOST=127.0.0.1
REDIS_HOST_PORT=6379
SPRING_DATA_REDIS_PASSWORD=<强密码>

# --- 检索/存储：方案 A（内存索引 + 本地盘） ---
PANEL_SEARCH_KEYWORD_BACKEND=memory
PANEL_SEARCH_VECTOR_BACKEND=memory
PANEL_SEARCH_RECOVER_INDEX_ON_START=true
PANEL_OBJECT_STORE=local
PANEL_OBJECT_STORE_LOCAL_DIR=/opt/panel/data/knowledge
PANEL_JOB_QUEUE=redis

# --- 安全 ---
JWT_SECRET=<openssl rand -base64 48>
PANEL_ENV=prod

# --- 注册开关（见注册方案 §2.3） ---
PANEL_SIGNUP_MODE=invite
PANEL_SIGNUP_INVITE_CODE=<随机 12 位>
PANEL_TURNSTILE_ENABLED=false

# --- 模型 ---
DASHSCOPE_API_KEY=<key>
```

生产**必须**删掉的三个开发默认值：`JWT_SECRET`（默认 `Panel-local-dev-secret-change-me-please-32bytes`）、`PLATFORM_ADMIN_PASSWORD`（默认 `123456`）、`SPRING_PROFILES_ACTIVE=dev`。

## 3. 首次部署（空机 → 可注册）

| 阶段 | 动作 | 验证 |
|---|---|---|
| 0 | 安全组放行 22/80/443；`ssh-keygen` 传公钥；关密码登录；`ufw` 默认拒绝 | 另开终端能登 |
| 1 | `apt install openjdk-21-jre-headless nginx mysql-server redis-server` | `java -version` / `nginx -v` |
| 2 | 建库建号（`CREATE DATABASE panel_ai ...`；`panel@127.0.0.1` 只授 `panel_ai.*`） | `mysql -upanel -p -h127.0.0.1 -e 'select 1'` |
| 3 | MySQL `bind-address=127.0.0.1`、`innodb_buffer_pool_size=256M`、`performance_schema=OFF` | `ss -tuln` 只有 127.0.0.1:3306 |
| 4 | Redis `bind 127.0.0.1`、`requirepass`、`maxmemory 256mb`、`appendonly no` | `redis-cli -a *** ping` |
| 5 | 本地 `mvn -f backend/pom.xml -DskipTests package`；`pnpm build`（或 `npm run build`） | 产出 jar 与 `dist` |
| 6 | 传 jar 到 `/opt/panel/releases/<ver>/`，软链 `current`；`dist` 传 `/var/www/panel/releases/<ver>/` | 文件属主 `panel:panel` |
| 7 | 写 `/etc/panel/*.env`（`chmod 600`）；装 `deploy/systemd/panel-backend@.service` 到 `/etc/systemd/system/` | `systemctl daemon-reload` |
| 8 | `systemctl enable --now panel-backend@blue` | `journalctl -u panel-backend@blue -f` 看到 Flyway 执行到 V11，端口 8080 |
| 9 | 装 Nginx 站点（`deploy/nginx/panel.conf`）、写 upstream 指向 8080、`nginx -t && reload` | `curl -I http://127.0.0.1/` 200 |
| 10 | 冒烟：注册 → 登录 → 传简历 → 开面试 → 刷题 | 全绿再对外 |

> 首次启动 Flyway 会从 V1 跑到 V11。**前 3 分钟别重启**，否则可能留半套 schema。硬中断的恢复方式：`flyway_schema_history` 里删掉失败那条，手工补齐该脚本，再重启。

## 4. 升级方案

### 4.1 版本与产物

- 版本号：`<UTC 时间戳>-<git sha7>`，例如 `20261113-a1b2c3d`。
- jar 只进 `releases/<ver>/`，**永不覆盖**；`current` 是软链。
- 前端同样按版本目录 + `current` 软链；`index.html` 设 `Cache-Control: no-store`，带 hash 的静态资源设 `immutable`。
- 构建只在本地/CI 做，服务器只跑 JRE。

### 4.2 数据库迁移纪律（最重要）

Flyway 只前进。三条铁律：

1. **不修改已执行过的脚本**（checksum 变了会直接启动失败）。
2. **一次发布内的迁移必须与旧版本兼容**（蓝绿时两个版本同时连库）。
3. 破坏性变更拆成三次发布（expand → migrate → contract）：

```sql
-- 发布 N：加列/加表，可空；旧代码不受影响
ALTER TABLE resume ADD COLUMN owner_user_id BIGINT NULL;

-- 发布 N+1：新代码双写 + 后台回填；旧代码仍可用
UPDATE resume SET owner_user_id = ... WHERE owner_user_id IS NULL;   -- 分批，每批 5000 行

-- 发布 N+2：读完切到新列后，才允许
ALTER TABLE resume MODIFY owner_user_id BIGINT NOT NULL;             -- 或不加 NOT NULL，永久保留 NULL 语义
```

本项目的 V11 就属于"发布 N"：只加可空列与索引，**旧 jar 打在新库上照样跑**，不需要停机窗口。

迁移前必须备份：

```bash
mysqldump --single-transaction --quick --triggers \
  -h127.0.0.1 -upanel -p"$MYSQL_PASSWORD" panel_ai | gzip > /opt/panel/backup/pre-$(date +%Y%m%d%H%M).sql.gz
```

> `--routines/--events` 需要额外权限（`mysql.proc`/`mysql.event`）；本项目没有存储过程与事件，别为了这两个参数去放大 `panel` 账号权限。

`clean-disabled: true` 已经在配置里开着，别关。

### 4.3 蓝绿发布流程

```
1. 备好 releases/<new>/panel-backend.jar
2. systemctl start panel-backend@green          # 8081，Flyway 在此跑
3. 循环 curl 127.0.0.1:8081/actuator/health 直到 UP（最长 180s）
4. 直连 8081 跑冒烟：登录、GET /resumes、GET /kb、开一场面试
5. 改 /etc/nginx/panel-upstream.conf 指向 8081 → nginx -t → reload
6. 观察 30 分钟：5xx、SSE 中断率、GC、DB 连接数
7. systemctl stop panel-backend@blue；把 current 软链指向新版本
```

回滚（30 秒）：

```bash
# 把 upstream 指回 8080，reload，绿实例留着排查
./deploy/scripts/switch-upstream.sh blue
```

蓝绿的前提是**无状态**：会话在 Redis、文件在本地盘（同一台机器共享）、任务队列在 Redis。所以同一台机器上的两个实例天然共享一切，不需要粘性会话。

### 4.4 发布检查单

发布前：

- [ ] 本地 `mvn -DskipTests package` 通过；`pnpm build` 通过
- [ ] 新迁移脚本与旧代码兼容（对照 §4.2 第 2 条）
- [ ] 已备份（`pre-<ts>.sql.gz` 存在且大小正常）
- [ ] 越权矩阵测试通过（注册方案 §3.5）
- [ ] 变更点里没有"默认值仍是开发默认"（JWT/admin 密码/dev profile）

发布后：

- [ ] `/actuator/health` = UP
- [ ] 注册 → 登录 → 上传简历 → 面试 → 刷题 五项冒烟通过
- [ ] 日志无 `ERROR` 突增、无 Flyway checksum 报错
- [ ] `ss -tuln` 对外仍只有 22/80/443

### 4.5 前端发布

```bash
rsync -a --delete dist/ /var/www/panel/releases/<ver>/
ln -sfn /var/www/panel/releases/<ver> /var/www/panel/current.new
mv -Tf /var/www/panel/current.new /var/www/panel/current   # 原子替换
```

只换软链，不 `reload` Nginx（静态文件是按请求读的）。回滚就是把软链指回上一版。

### 4.6 功能开关

灰度优先用配置，不要先发代码再改行为：

```properties
PANEL_SIGNUP_MODE=open|invite|closed      # 注册闸门
PANEL_KB_QUIZ_SKILL_WEIGHT=true|false     # 抽题权重 A/B
PANEL_KB_GRAPH_ENABLED=false              # 图谱通道
PANEL_SPEECH_ENABLED / PANEL_ASR_ENABLED  # 语音能力
```

改完 `systemctl reload-or-restart` 两个实例，按 §4.3 顺序切。

## 5. 回滚决策表

| 情况 | 动作 | 数据影响 |
|---|---|---|
| 新版本逻辑错误、迁移向后兼容 | upstream 切回旧实例 | 无 |
| 新版本写坏了数据 | 切回 + 用备份整库还原到故障前 | 丢失故障后写入 |
| 迁移不可逆（改类型/删列） | 切回 + 还原 `pre-*.sql.gz` | 同上，必须有备份 |
| 前端白屏 | 软链回上一版 | 无 |
| 对象存储被误删 | 从每日 `rsync` 备份拉回 `data/knowledge` | 当天新增文件缺失 |

原则：**应用故障用切流，数据故障用还原**。不要试图写 SQL 逆向修数据，除非能证明影响面只有几行。

## 6. 备份与恢复

### 6.1 备份（每日 03:10）

```bash
# deploy/scripts/backup.sh 干的四件事
mysqldump --single-transaction --quick --routines --triggers panel_ai | gzip > backup/db-$(date +%F).sql.gz
tar -czf backup/objects-$(date +%F).tgz -C /opt/panel/data knowledge
find backup -name 'db-*.sql.gz' -mtime +14 -delete
find backup -name 'objects-*.tgz' -mtime +7 -delete
```

再 `rsync` 到 COS/异地（免费额度够用）。保留 14 天日备 + 每月 1 份月备。

### 6.2 恢复演练（每月一次，必须真跑）

```bash
mysql -e 'DROP DATABASE IF EXISTS panel_ai_restore; CREATE DATABASE panel_ai_restore'
gunzip -c backup/db-2026-11-13.sql.gz | mysql panel_ai_restore
mysql -N -e "SELECT COUNT(*) FROM information_schema.tables WHERE table_schema='panel_ai_restore'"   # 应 ≈ 35+
```

只备份不演练，等于没备份。

## 7. 监控与告警（全免费）

| 项 | 做法 |
|---|---|
| 存活 | `*/2 * * * * curl -fs localhost:8080/actuator/health >/dev/null || systemctl restart panel-backend@blue`（先告警再重启） |
| 外部可用性 | Uptime Kuma（自建，1 个容器）探 `https://<域名>/` 与 `/api/v1/auth/login` |
| 资源 | `node_exporter` + Grafana 太重；起步用 `vmstat 1`、`journalctl --since`、MySQL `SHOW PROCESSLIST` |
| 慢查询 | MySQL `slow_query_log=ON`, `long_query_time=1` |
| 日志 | logrotate 切 `/opt/panel/logs/*.log`；`journalctl --vacuum-time=14d` |
| 业务 | 每日 `SELECT COUNT(*) FROM sys_user WHERE created_at > NOW()-INTERVAL 1 DAY`，异常暴涨即被刷 |

## 8. 常见故障对照

| 现象 | 先查 | 处理 |
|---|---|---|
| 启动即退出，日志有 Flyway checksum | `flyway_schema_history` vs 脚本 | 恢复原脚本内容；绝不 `repair` 掩盖 |
| 登录 500 / `DEPENDENCY_UNAVAILABLE` | Redis 是否带密码、`SPRING_DATA_REDIS_PASSWORD` | 改 `.env` 重启 |
| 上传后一直 PENDING | 任务队列后端、`RedisStreamPersistentJobQueue` 是否降级 | `PANEL_JOB_QUEUE=mysql` 兜底 |
| 检索全空 | 内存索引未重建 | `PANEL_SEARCH_RECOVER_INDEX_ON_START=true` 或手动 `POST /kb/documents/{id}/reindex` |
| 回答"攒完才出" | Nginx `proxy_buffering off` / `X-Accel-Buffering no` | 改配置 reload |
| 面试语音连不上 | `/ws/` 未配 Upgrade | 补 Nginx location |
| 磁盘满 | `/opt/panel/logs`、`/tmp/panel-knowledge`（对象存储没配本地目录） | 配 `PANEL_OBJECT_STORE_LOCAL_DIR` + 清日志 |

## 9. 与注册/隔离方案的衔接

1. V11 迁移随第一个带隔离代码的版本一起上（§4.2 的"发布 N"）。
2. 注册功能上线前必须先关掉公开的 `/api/v1/auth/register`，否则任何人都能建 `ADMIN` 租户。
3. 邮件服务（SMTP）不落地时，注册只能走邀请码模式；别开 `open` 又没验证手段。
4. 隔离上线后跑一遍 §3.5 越权矩阵，再放流量。
