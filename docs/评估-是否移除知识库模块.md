# 评估：部署时不带知识库模块

日期：2026-11-12 · 结论：**不建议物理移除，建议"部署 + 开关关闭"**

## 一、一句话结论

`knowledge` 不是独立业务模块，它是**简历解析、OCR、AI 对话、租户配额四个模块的共享基础设施**。物理删掉它，简历功能会一起废掉，而且**省不到任何中间件**——因为 memory/local 方案已经把 ES/Milvus/MinIO/Kafka 全清零了。

## 二、代码证据：谁在依赖 knowledge

| 依赖方 | 依赖的具体类 | 物理移除后果 |
|---|---|---|
| `interview`（6 个类）<br>ResumeService / ResumePreviewService / ResumeParseWorker / ResumeParsingService / ResumeMarkdownRenderer / ResumeAnalysisService | `KnowledgeObjectStore`（原文件存取）<br>`DocumentParserRegistry`（PDF/DOCX 解析）<br>`DocumentBlock` / `ParsedDocument` | **简历上传、解析、预览、分析全部编译失败** |
| `ai`（2 个类）<br>DefaultAiChatService / KnowledgeSearchHarnessPlugin | `KnowledgeSearchService`（**构造器硬注入，无 @Nullable**）<br>`KnowledgeSearchCitations` | **AI 对话 Bean 创建失败 → Spring 启动直接崩** |
| `ocr`（1 个类） | `KnowledgeObjectStore` | OCR 解析失败 |
| `tenancy`（1 个类） | `KnowledgeDocumentRepository` | 租户配额统计失败 |
| 自身（200 个文件） | 11 个 Controller、12 张 `kb_*` 表、检索/切片/图谱 | — |

**根因**：当初从 GymMind 迁移时，`knowledge.infrastructure.parser.*`（文档解析）和 `KnowledgeObjectStore`（对象存储）没有下沉到 `shared`，导致"知识库业务"和"文档基础设施"耦合在同一个包里。简历功能复用的正是后者。

## 三、成本收益账（这张表是评估的核心）

| 维度 | 砍掉 KB | 保留 KB + memory/local | 真实差别 |
|---|---|---|---|
| MySQL | 需要 | 需要 | **0** |
| Redis | 需要 | 需要 | **0** |
| ES / Milvus / MinIO / Kafka | 不需要 | 不需要 | **0** ← 关键 |
| jar 体积 | pdfbox / poi 简历也要用，省不掉；minio 客户端约 1 MB | — | ≈0 |
| 堆内存 | 没数据时索引本来不占 | 几千片约 20 MB | ≈0（可忽略） |
| 启动耗时 | Flyway 的 `kb_*` 表在同一份 V1 里，照建 | — | ≈0 |
| embedding 费用 | 省（不调用） | 不上传文档也不调用 | **0** |
| HTTP 暴露面 | 少 11 个 Controller | 多 11 个 | 有差别 |
| 前端体积 | 少 6 页 + 4 个 api 模块 | 多这些 | 有差别 |
| **将来恢复成本** | **高**：重接 300 处 import、重写前端 6 页 | 0（改开关即可） | **唯一的实质代价** |

结论：**"为了轻量化而砍知识库"这个动机不成立**。砍与不砍，运行时都是 MySQL + Redis 两个中间件进程。

## 四、三种做法对比

### 方案 ①：部署 + 开关关闭（推荐，2 小时，零风险）

- 11 个 KB Controller 加 `@ConditionalOnProperty(name = "panel.kb.enabled", havingValue = "true", matchIfMissing = true)`
- `.env` 设 `PANEL_KB_ENABLED=false`
- 前端 `App.tsx` 注释 6 条 `/kb*` 路由 + 侧边菜单项，`src/api/{kb,questions,quiz,catalog}.ts` 保留不打包
- `platform-default-plugins` 去掉 `knowledge_search`（否则空库检索会走 `empty-knowledge-policy: DISCLOSE`）
- 简历 / 面试 / AI 对话主链路完全不受影响（它们只用 parser + object store）
- 随时 `PANEL_KB_ENABLED=true` + 重启即可恢复全部能力

### 方案 ②：物理移除（不推荐，1–2 天，中高风险）

1. 把 `knowledge/infrastructure/parser/**`（约 12 个类）+ `KnowledgeObjectStore` 抽到 `shared/document`
2. 改 `interview` 6 个类 + `ocr` 1 个类的 import
3. `DefaultAiChatService` 的 `KnowledgeSearchService` 改成可选依赖（`@Nullable` 或接口 + 空实现）
4. harness 插件表去掉 `knowledge_search`
5. pom 排除 `com/panel/knowledge/**`
6. **Flyway 无解**：`V1__baseline.sql` 里 12 张 `kb_*` 表删不掉——改 V1 会让已有库 checksum 校验失败（`baseline-on-migrate` 救不了已执行过的迁移）

收益仅为"接口面收敛"，代价是 1–2 天 + 未来恢复成本。

### 方案 ③：全留（原计划）

memory + local，2 小时上线，知识库变"可选功能"：想用就上传文档，不用就空着，不消耗任何外部资源。

## 五、推荐落地

**方案 ③ 打底 + 方案 ① 的开关**：

```
代码全留  →  一次部署，两条产品线都能走
开关默认关  →  PANEL_KB_ENABLED=false，11 个接口不外露
核心链路完整 →  简历解析依赖 parser，不受开关影响
零 embedding 支出 →  没人上传文档就不调百炼
随时可开  →  改一个环境变量 + 重启
```

## 六、两个必须点明的坑

1. **`kb_*` 表删不掉**：物理移除代码也不会移除表，因为 Flyway V1 已包含它们，改历史迁移会 checksum 失败。数据库层面本来就不可能"干净移除"。
2. **AI 对话是硬依赖**：`DefaultAiChatService` 构造器要 `KnowledgeSearchService`，没有 `@Nullable`，删包就是启动失败——不是"功能降级"，是"服务起不来"。
