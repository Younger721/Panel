# 知识目录与 LLM 自动归类 · 设计方案

> 状态：P0 + 自动归类 + 人工校正 + 检索过滤已落地（2026-11-10），剩余 LLM 新建目录审批与建议复核见 §0.1  
> 目标：把现在“平铺的文档 / 题目列表”升级为“左侧树形知识目录 + 右侧知识点内容”，上传后由 LLM 自动归类，人工可校正。

## 0. 已确认决策（2026-11-09）

| 决策 | 结论 |
| --- | --- |
| 树的范围 | 每个 KB 一棵树，互不共享 |
| 知识点粒度 | chunk 本身即知识点（MVP 不生成摘要卡片） |
| LLM 新建目录 | 必须人工确认后才进入正式树 |
| 层级 | 最多 3 级 |
| 题库 / 技术文档命名 | 共用 `path_key` 词表（如 `redis/single-thread`） |
| 存量数据初始化 | 已为 E2E KB 6/7 种演示树 |

## 0.1 落地状态

已完成：

| 层 | 内容 |
| --- | --- |
| 表 | `kb_category`（树，`path` + `path_key`，最多 3 级）、`kb_item_category`（chunk/question 多标签 + primary + locked）；Flyway `V5` / `V6` |
| 后端 | `GET /api/v1/kb/{kbId}/catalog/tree`；`POST /{kbId}/catalog/categories`；`PATCH /catalog/categories/{id}`；`POST /catalog/categories/{id}/move`；`DELETE /catalog/categories/{id}`；`GET /catalog/categories/{id}/items?kbId=&type=&offset=&limit=`；`POST/DELETE .../items` 挂载与摘除；`POST /{kbId}/catalog/items/move` 绝对移动（清旧归属）；`POST /{kbId}/catalog/classify` 手动重跑 |
| 自动归类 | `KbAutoClassifyService`：优先 LLM 在已有目录中选一个（`categoryId + confidence`），失败/低置信度退回关键词规则；置信度 ≥ 0.72 才落库，其余留在“未分类”；人工挂载 `locked=true` |
| 人工校正 | 卡片级“移动”弹窗：选目标目录或“未分类（移出所有目录）”，后端一次事务清旧挂载再写新挂载；选中非系统目录时可重命名、删除空目录 |
| 入库钩子 | 切片与题目落库后调用自动归类；文档删除/重新切片时同步清理 `kb_item_category`，避免孤儿计数 |
| 检索过滤 | `KbSearchRequest.categoryIds` 在 RRF 融合后按目录子树过滤所有通道（BM25 / 向量 / 图谱）；`KbCatalogService.chunkKeysInCategories` 把子树内切片映射为 ES chunkKey；检索页提供“目录”下拉 |
| 前端 | `/kb/:id/catalog` 左侧树 + 右侧内容：选中父目录时按一级子目录分组（每组带数量与预览，可点“查看子目录”进入），选中叶子节点时只展示该节点条目；支持新建、重命名、删除、移动条目、手动“自动归类”；顶部“文档 N”进入文档列表 |
| 批量上传 | 知识库详情页文件框支持多选；前端逐个上传，后端 `kbIngestExecutor` 最多 4 个文档并发解析；单文档最多 500 题 |
| 自动建目录 | 题库只按题目归类（不按来源 chunk）；LLM 优先复用已有目录，没有合适目录时返回 `path` 并自动创建 1~3 级目录；低于 0.72 留未分类 |
| 分组语义 | `GET /catalog/categories/{id}/items` 对父目录返回 `groups`：每个一级子目录的子树总数 + 前 6 条预览；`items` 为直接挂在父目录本身的条目。子目录再点进去递归同样的规则，最多 3 级 |
| 演示数据 | KB 6 三级树（Java/MySQL/网络/Redis，题目已挂载）；KB 7 Redis 二级树（5 个切片全部挂载），两库共用 `redis/single-thread` 等 pathKey |

待做：

1. 自动归类建议的人工复核队列（当前高置信度直接落库，低置信度留未分类）。
2. LLM 自动生成新目录的审批流（当前只允许在已有目录中选）。
3. 目录节点拖拽排序 / 跨父级拖拽（当前后端支持 move，前端未暴露）。

## 1. 目标与边界

### 要做

1. 每个知识库有一棵可维护的目录树（领域 → 主题 → 知识点）。
2. 左侧点目录节点，右侧展示该节点下的知识点 / 题目 / 来源文档。
3. 上传文档或题目后，LLM 自动判断应归入哪个节点；识别不了就进“未分类”。
4. 归类结果可人工接受、改挂、合并节点；人工结果优先，不被后续自动任务覆盖。
5. 目录分类能作为检索过滤条件，和现有 BM25 + 向量 + 图谱链路打通。

### 不做（本期）

- 不做跨知识库的全局知识图谱编辑器。
- 不改现有切片、向量化、图谱抽取主链路。
- 不做多人协同编辑 / 审批流。
- 不做自动生成完整课程体系（只做归类，不重写内容）。

## 2. 现状与差距

现在已有：

- `kb_document` / `kb_chunk`：文档与切片。
- `kb_question`：题库文档解析出的题目。
- `kb_concept` / `kb_graph_edge` / `kb_graph_mention`：自动抽取的概念图谱。
- 检索：ES BM25 + Milvus 向量 + RRF + 图谱通道。

缺的是“编辑层面的分类”：

- 文档、题目都是平铺列表，只能靠关键词搜。
- 没有稳定的主题路径，无法回答“Redis 下有哪些知识点”。
- 图谱概念是网状实体，不适合当目录：概念会爆炸、没有层级、不适合人工维护。

**关键区分：**

| | 目录（Category） | 概念（Concept） |
| --- | --- | --- |
| 形态 | 树，最多 3 层 | 网状 |
| 来源 | 人工 + LLM 建议 | LLM 自动抽取 |
| 用途 | 浏览、组织、过滤 | 检索扩展、关联 |
| 可编辑 | 是 | 否（可审核） |
| 稳定性 | 高 | 随文档变化 |

两者不混用。目录节点可以在 P2 关联概念，用于“该目录下的热门概念”，但不把概念直接塞进树。

## 3. 核心模型

### 3.1 一棵树属于一个知识库

推荐：**每个 KB 一棵树**。

- 面试题库有自己的树：Java / 并发 / 线程池；MySQL / 索引；Redis / 持久化……
- 技术文档有自己的树，但节点命名规范一致。
- 后续需要跨库统一时，用 `path_key` 对齐（如 `java/concurrency/threadpool`），不强行共用一张表。

不推荐一开始做“全局唯一知识树”：不同 KB 的颗粒度、命名习惯不同，容易互相污染。

### 3.2 知识点是什么

MVP：**一个 chunk 就是一个知识点**。

- 标题用 chunk.heading；
- 摘要用 chunk 前 120–200 字；
- 来源保留 document + ordinal + pageNo；
- 不新增“知识点正文”表，避免重复存储。

P2 再引入 `kb_knowledge_point`：把同一叶子下多个 chunk 用 LLM 合成一张“知识点卡片”，卡片里保留 chunk 引用。这样既有结构化摘要，又不丢原文。

### 3.3 多归属

一个 chunk / 题目可以属于多个目录节点（例如“缓存穿透”既属于 Redis，也属于系统设计）。

- `kb_item_category` 是多对多；
- 有一个 `is_primary` 标记主分类，用于树计数和默认展示；
- 其余归属在详情里显示为“也属于”。

### 3.4 系统节点

- **未分类**：系统节点，永远存在，不可删除；LLM 置信度低或解析失败的内容进这里。
- **待确认**：不是树节点，而是顶部的一个筛选入口，汇总低置信度建议。

## 4. 信息架构与页面

### 4.1 入口

新增“知识目录”概念，落在 KB 详情页：

```
/kb/:id            知识库详情（文档、切片、设置）
/kb/:id/catalog    知识目录（本次新增，三栏）
/kb/questions      题库总览（保留，可进入某个题库的 catalog）
```

侧边栏“知识库管理”保持不变；“面试题库”进入题库列表后，点某个题库进入 `/kb/:id/catalog`。

### 4.2 三栏布局

```
┌──────────────────────────────────────────────────────────────────────────┐
│  面试题库 · 知识目录                    [搜索目录] [重新归类] [+ 上传]      │
├──────────────────┬───────────────────────────────────────────────────────┤
│ ▾ Java      24   │  Java › 并发 › 线程池                    12 个知识点   │
│   ▾ 并发    12   │  ┌─────────────────────────────────────────────────┐  │
│     线程池   8   │  │ 线程池核心参数与拒绝策略          来源 2 篇      │  │
│     锁       4   │  │ 核心线程数、最大线程数、队列、拒绝策略……        │  │
│   ▸ 集合     9   │  │ [Java] [并发] [线程池]       查看原文 →         │  │
│ ▸ MySQL     18   │  └─────────────────────────────────────────────────┘  │
│ ▸ Redis     15   │  ┌─────────────────────────────────────────────────┐  │
│ ▸ 计算机网络 11   │  │ 为什么不用 Executors 创建线程池                  │  │
│                   │  │ ……                                              │  │
│ ─────────────     │  └─────────────────────────────────────────────────┘  │
│ 未分类       3    │                                                       │
└──────────────────┴───────────────────────────────────────────────────────┘
```

- 左栏 260–280px，可折叠。
- 中栏是内容区，不固定宽度，卡片自适应 2 列（宽屏）。
- 点卡片右侧滑出详情抽屉，展示完整 chunk、来源、概念、所属目录。

### 4.3 左栏交互

- 展开 / 收起：状态存 localStorage，按 KB 记忆。
- 搜索：输入关键词过滤树，命中节点自动展开并高亮，显示“命中 N 个知识点”。
- 计数：每个节点显示该节点（含子节点）下的知识点数；题库 KB 同时显示题目数，用 `8 题` 小标签。
- 右键 / 悬停菜单：
  - 新建子目录
  - 重命名
  - 移动到…
  - 合并到…
  - 删除（子内容移到“未分类”）
- 拖拽：P1 支持把知识点卡片拖到另一个节点，写入 `source=MANUAL` 并加锁，后续自动归类不覆盖。
- “未分类”固定在底部，不可删除、不可移动。

### 4.4 右栏内容

顶部：

- 面包屑：`Java / 并发 / 线程池`
- 节点描述（可选，LLM 生成一句话）
- 统计：知识点 12 · 题目 8 · 来源文档 3
- `重新归类此节点`（只对当前子树）

Tab：

1. **知识点**（chunk 卡片）
2. **题目**（仅题库 KB；题干 + 公司/年份/难度 + 关联技术文档）

父目录的内容组织（已落地）：

- 先展示“直接挂在本目录”的条目（如果有）。
- 再按一级子目录分组：组头 = 子目录名 + 子树总数，组内 = 前 6 条预览。
- 点组头进入该子目录；如果它还有子目录，继续按同样规则分组，最多 3 级。
- 叶子节点不分组，直接平铺该节点下的全部条目。

文档入口：

- 顶部“文档 N”进入 KB 文档列表；文档行可预览切片、发布、重解析。
- 每张知识点卡片可点“查看详情”在右侧抽屉直接读完整切片/题目，不需要跳来源页；卡片仍保留来源文档名。

空状态：

- 无内容：“这个目录还没有内容，上传文档或把已有知识点拖进来。”
- 未分类：“有 3 个切片未归类，去确认 →”

### 4.5 上传与归类流程

上传弹窗增加“归类方式”：

```
上传文档
[选择文件]
归类方式：
  ● 自动归类（推荐）
  ○ 先放入未分类，稍后手动整理
[上传]
```

上传后进度条：

```
解析中 → 切片中 → 向量化中 → AI 归类中 → 完成
                              ↑ 可跳过，不阻塞文档可用
```

归类是异步的，不阻塞文档 READY；归类完成后左侧树增量刷新，顶部出现“AI 新增 4 个目录，待确认 6 项”。

### 4.6 待确认抽屉

```
待确认 6 项                                    [全部接受高分项]
┌──────────────────────────────────────────────────────────────┐
│ 线程池核心参数与拒绝策略                                      │
│ 建议：Java / 并发 / 线程池        置信度 0.82                  │
│ 理由：标题与内容都围绕线程池参数、队列、拒绝策略               │
│ [接受] [改到其他节点] [新建目录] [忽略]                        │
├──────────────────────────────────────────────────────────────┤
│ Redis 大 key 怎么处理                                        │
│ 建议：Redis / 性能 / 大 key       置信度 0.58  ⚠ 需确认        │
└──────────────────────────────────────────────────────────────┘
```

高分（≥0.75）默认直接落库，但仍可在历史里回看；低分进待确认。

## 5. 数据模型

### 5.1 目录表

```sql
CREATE TABLE kb_category (
  id            BIGINT PRIMARY KEY AUTO_INCREMENT,
  kb_id         BIGINT NOT NULL,
  parent_id     BIGINT NULL,
  name          VARCHAR(64) NOT NULL,
  path          VARCHAR(512) NOT NULL,      -- /1/7/23/，用于子树查询
  path_key      VARCHAR(512) NOT NULL,      -- java/concurrency/threadpool
  depth         TINYINT NOT NULL,
  description   VARCHAR(512) NULL,
  sort_no       INT NOT NULL DEFAULT 0,
  source        VARCHAR(16) NOT NULL,       -- SYSTEM / LLM / MANUAL
  status        VARCHAR(16) NOT NULL,       -- ACTIVE / PENDING / ARCHIVED
  created_at    DATETIME NOT NULL,
  updated_at    DATETIME NOT NULL,
  UNIQUE KEY uk_kb_parent_name (kb_id, parent_id, name),
  UNIQUE KEY uk_kb_path_key (kb_id, path_key),
  KEY idx_kb_path (kb_id, path(191))
);
```

- `path` 用于 `LIKE '/1/7/%'` 查子树，200 篇文档规模足够。
- `path_key` 用于跨 KB 对齐、合并建议。
- 改名 / 移动时重算整棵子树的 `path` / `path_key`。

### 5.2 归属表

```sql
CREATE TABLE kb_item_category (
  id          BIGINT PRIMARY KEY AUTO_INCREMENT,
  kb_id       BIGINT NOT NULL,
  item_type   VARCHAR(16) NOT NULL,   -- CHUNK / QUESTION / DOCUMENT
  item_id     BIGINT NOT NULL,
  category_id BIGINT NOT NULL,
  is_primary  TINYINT(1) NOT NULL DEFAULT 0,
  confidence  DECIMAL(4,3) NULL,
  source      VARCHAR(16) NOT NULL,   -- LLM / RULE / MANUAL
  locked      TINYINT(1) NOT NULL DEFAULT 0,
  created_at  DATETIME NOT NULL,
  UNIQUE KEY uk_item_category (item_type, item_id, category_id),
  KEY idx_category (category_id, item_type),
  KEY idx_item (item_type, item_id)
);
```

- `locked=1`：人工确认过，重新归类时跳过。
- `is_primary`：每个 item 只有一个主分类；插入时先清旧 primary。

### 5.3 归类任务与建议

```sql
CREATE TABLE kb_classify_run (
  id            BIGINT PRIMARY KEY AUTO_INCREMENT,
  kb_id         BIGINT NOT NULL,
  document_id   BIGINT NULL,
  scope         VARCHAR(16) NOT NULL,    -- DOCUMENT / QUESTION / KB
  model         VARCHAR(64) NOT NULL,
  prompt_version VARCHAR(32) NOT NULL,
  status        VARCHAR(16) NOT NULL,    -- RUNNING / SUCCEEDED / FAILED
  item_count    INT NOT NULL DEFAULT 0,
  token_usage   INT NULL,
  error         VARCHAR(1024) NULL,
  started_at    DATETIME NOT NULL,
  finished_at   DATETIME NULL
);

CREATE TABLE kb_classify_suggestion (
  id            BIGINT PRIMARY KEY AUTO_INCREMENT,
  run_id        BIGINT NOT NULL,
  kb_id         BIGINT NOT NULL,
  item_type     VARCHAR(16) NOT NULL,
  item_id       BIGINT NOT NULL,
  category_id   BIGINT NULL,             -- 建议挂到的已有节点
  proposed_path VARCHAR(512) NOT NULL,   -- 建议的新路径（JSON 数组亦可）
  confidence    DECIMAL(4,3) NOT NULL,
  reason        VARCHAR(512) NULL,
  status        VARCHAR(16) NOT NULL,    -- PENDING / ACCEPTED / REJECTED
  created_at    DATETIME NOT NULL
);
```

### 5.4 计数

MVP 直接按 `path` 前缀 + 关联表 count：

```sql
SELECT c.id, COUNT(DISTINCT ic.item_id)
FROM kb_category c
JOIN kb_category d ON d.path LIKE CONCAT(c.path, '%')
JOIN kb_item_category ic ON ic.category_id = d.id AND ic.item_type = 'CHUNK'
WHERE c.kb_id = ?
GROUP BY c.id;
```

数据量小（< 1 万切片）可直接查；后续加 5 分钟缓存或计数表。

## 6. LLM 自动归类

### 6.1 触发时机

| 场景 | 触发 |
| --- | --- |
| 文档上传完成 | 异步任务，按 document 归类 |
| 题库解析完成 | 按 question 批量归类 |
| 手动“重新归类” | 按 KB / 节点 / 文档 |
| 目录结构大改 | 只对新内容归类，旧内容不动 |

不阻塞文档 READY；归类失败不影响问答。

### 6.2 输入

- KB 类型（QUESTION_BANK / TECH_DOC / JOB_KNOWLEDGE）
- 文档标题、文件名、已有的 hashtag / 标签
- 该 KB 现有目录树（只传 `path_key + name`，最多 200 个节点，按使用频率排序）
- 题目：题干 + 答案摘要；文档：每个 chunk 的 heading + 前 400 字

控制单次请求在 4k tokens 内；一篇文档一次调用，避免逐 chunk 调用。

### 6.3 输出契约

```json
{
  "assignments": [
    {
      "itemType": "CHUNK",
      "itemId": 123,
      "path": ["Java", "并发", "线程池"],
      "confidence": 0.86,
      "reason": "标题和内容都围绕线程池参数与拒绝策略"
    }
  ],
  "newNodes": [
    { "path": ["Java", "并发", "AQS"], "reason": "现有目录没有 AQS 节点" }
  ]
}
```

服务端校验：

- 路径深度 ≤ 3；
- 节点名 2–16 字，去首尾空白、去标点；
- 优先复用已有节点（同名 / 同 path_key / 别名）；
- 新节点置信度 ≥ 0.8 才创建，且状态为 `PENDING`；
- 所有 assignment 置信度 < 0.5 → 未分类；
- 0.5–0.75 → 建建议，不直接落库；
- 同一 chunk 多标签最多 3 个。

### 6.4 去重与合并

- 名称归一化：小写、去空格、去标点、全半角统一。
- 别名表：`thread pool` / `线程池` 指向同一 `path_key`。
- 新节点与已有节点相似度高（编辑距离 / 包含关系）→ 合并建议，不新建。
- “Java 并发”和“并发编程”这种，进待确认，由人决定。

### 6.5 人工优先

- 人工接受 / 改挂 → `source=MANUAL`, `locked=1`。
- 重新归类时：
  - `locked=1` 跳过；
  - 只删除 `source=LLM` 且 `locked=0` 的旧归属；
  - 不动人工结果。

### 6.6 成本与幂等

- 按 `content_hash + prompt_version + model` 缓存结果，重复上传不重复调用。
- 单文档一次调用；200 篇文档约 200 次，远低于逐 chunk 调用。
- 失败重试 2 次，仍失败 → 全部进未分类，并记录 run.error。
- Prompt 版本化，升级后可批量重跑。

## 7. 检索融合

现有 `KbSearchService` 增加目录过滤：

```json
{
  "query": "线程池参数怎么配",
  "kbId": 6,
  "categoryIds": [12],
  "includeDescendants": true
}
```

- 服务端把 `categoryIds` 展开成子树节点集合；
- 召回阶段：ES 加 `category_id` 过滤（需在索引里冗余 `categoryIds` 字段），Milvus 结果后置过滤；
- 融合后再做一次 `filterChunkKeys` 校验，保证向量命中同样受目录约束；
- 可选：命中主分类与查询分类一致时加小幅 boost（如 ×1.05），不做硬性。
- 问答页的知识库选择器旁增加“目录范围”下拉，默认全库。

题库 → 技术文档的关联（现有 `references`）可以升级为：

1. 先按同 `path_key` 找技术文档 chunk；
2. 再走概念链接兜底；
3. 两者合并去重。

## 10. 迁移与分期

### P0：目录骨架（可用，不依赖 LLM）

1. Flyway 新建 4 张表。
2. 规则初始化目录：
   - 技术文档：按 `heading` 的一级标题建节点；
   - 题库：按题目 tags / 题干关键词映射；
   - 全部先落 `未分类`，再人工拖。
3. 左树 + 右列表 + 计数 + 手动新建/改名/移动。
4. 检索支持 `categoryIds`。

### P1：LLM 自动归类

1. `KbClassifyService` 异步任务 + 队列。
2. 文档 / 题目归类，写 suggestion。
3. 待确认抽屉、接受/拒绝、批量接受高分。
4. 重新归类、幂等缓存、失败降级。
5. 存量数据一次性 backfill。

### P2：增强

1. 叶子节点 LLM 汇总成“知识点卡片”。
2. 拖拽移动、合并建议、别名管理。
3. 跨 KB 目录对齐（同 `path_key` 共享）。
4. 目录级问答范围、目录热度统计。

## 11. 风险与对策

| 风险 | 对策 |
| --- | --- |
| LLM 乱建节点，树越来越碎 | 新节点需 ≥0.8 且人工确认；相似节点合并建议；限制深度 3 |
| 归类错误污染目录 | 低分进待确认；人工结果锁定；可一键重跑 |
| 改名/移动导致 path 失效 | 事务内重算子树 path；path_key 唯一约束 |
| 重新归类覆盖人工结果 | `locked` + 只删 LLM 来源记录 |
| 树计数慢 | 索引 + path 前缀；数据量大后加缓存 |
| 题目和技术文档目录对不上 | 统一 path_key 命名规范；P2 做对齐 |
| 上传变慢 | 归类异步，不阻塞 READY；失败降级未分类 |

## 12. 待确认的产品决策

1. **树的范围**：每个 KB 一棵树（推荐），还是所有 KB 共用一棵全局树？
2. **知识点粒度**：先用 chunk 当知识点（推荐 MVP），还是必须 LLM 合成摘要卡片？
3. **新节点**：LLM 新建的目录直接可见，还是必须人工确认后才出现在树里？
4. **层级**：固定最多 3 层（推荐），还是允许 4 层？
5. **题库与技术文档**：是否共用同一套 path_key 命名（推荐，便于题目关联文档）？
6. **历史数据**：现有 4 道题 + 5 个技术切片，是否要我按建议目录先人工初始化一版给你看效果？

## 13. 验收标准

- 上传一篇新文档，30 秒内左侧树出现对应节点，计数 +1；低置信度内容进“未分类”。
- 点任意节点，右侧 1 秒内展示其下知识点，分页正常。
- 手动把知识点拖到另一个节点后，重新归类不会把它移回去。
- 搜索时加目录范围，召回结果只来自该子树。
- 改名 / 移动节点后，子节点 path、计数、面包屑全部正确。
- 未分类、空目录、归类失败三种状态都有明确空态和出口。
