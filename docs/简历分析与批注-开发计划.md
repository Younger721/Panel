## 1. 背景与目标

现有代码已经能"上传简历 → 抽结构化画像 → 出题 → 评分 → 报告"，但有三个断层：

| 断层 | 现状 | 目标 |
|---|---|---|
| 没有中间层 | 直接从 PDF/DOCX 抽 JSON 画像，看不到原文结构 | 落一份 Markdown + 块结构，前端能按原版式渲染 |
| 没有细粒度批注 | 只有整体画像 | 按模块 → 小点逐条点评，带原文锚点，像 Word 批注 |
| 面试参数太粗 | 一个 `turnBudget` | 题数 N + 追问上限 M，两个独立参数 |

**一句话目标**：用户上传一份简历，能在网页上看到一份带批注的简历——每条批注说明"这个点写得好不好、怎么改"，并附 3 个参考问题；然后可以按自定义题数开始一场会追问的模拟面试，结束后留下可回看的记录。

---

## 2. 范围

### 做

1. 多格式简历上传（PDF / DOCX / TXT / MD）→ 文本 → **Markdown + 块结构**
2. 模块切分：个人介绍 / 教育 / 实习经历 / 项目经历 / 技术栈 / 其他
3. 小点级点评：等级（强/中/弱）+ 点评 + 优化建议 + **3 个参考问题**
4. 批注锚点：`blockId + start + end`，支持句子级高亮
5. 前端批注页：A4 渲染 + 右侧批注栏 + 连线 + 悬浮联动（放大/模糊）
6. 面试设置页：题数 N、追问上限 M
7. 动态追问：答得浅才追问，最多 M 次
8. 面试记录：列表 + 详情 + 每场总结

### 不做

- 知识库入库、ES/Milvus 检索、Rerank
- 岗位匹配、多租户
- 简历在线编辑（只读展示；编辑会让锚点全部失效）
- 导出 PDF（后期再说）

## 3. 用户流程

```
① 上传简历 ──> 解析中（PARSING）──> 分析中（ANALYZING）──> PARSED
                                                        │
② 批注页：左简历右批注，悬浮联动  <────────────────────┘
   │
   ├─ 点批注里的参考问题 → 看问题，不进面试
   │
③ 点"开始模拟面试" ──> 设置页：题数 N（3-10）、追问上限 M（0-3）
   │
④ 面试页：逐题问答（SSE 流式显示"面试官正在出题/评分"）
   │   答得浅 → 就同一小点追问（≤M 次）
   │   答得好 → 换下一个未覆盖的小点
   │
⑤ 结束 → 报告页（总分 + 每个小点得分 + 证据引用）
   │
⑥ 历史页：所有面试记录列表，可回看任意一场
```

## 4. 数据模型

单租户，所有新表**不带 `tenant_id`**。

### 4.1 新增 `resume_analysis`

一份简历一行，整棵分析树存 JSON（读取时永远整篇一起读，没有跨简历查小点的需求）。

```sql
CREATE TABLE resume_analysis (
  id          BIGINT PRIMARY KEY AUTO_INCREMENT,
  resume_id   BIGINT       NOT NULL UNIQUE,
  markdown    LONGTEXT     NOT NULL,   -- 转换后的 MD 全文，可下载
  blocks_json LONGTEXT     NOT NULL,   -- 块结构（锚点坐标系）
  modules_json LONGTEXT    NOT NULL,   -- 模块 → 小点 → 批注
  model_name  VARCHAR(128),
  created_at  DATETIME(6)  NOT NULL,
  CONSTRAINT fk_analysis_resume FOREIGN KEY (resume_id) REFERENCES resume(id)
);
```

### 4.2 改造 `resume`

```
status: PENDING → PARSING → ANALYZING → PARSED / FAILED   （新增 ANALYZING）
```

删除简历走**软删除**（`V7__resume_soft_delete.sql`）：只落删除时间戳，不删行、不动对象存储、不级联清 `resume_profile` / `resume_analysis`。

```sql
ALTER TABLE resume
  ADD COLUMN deleted_at DATETIME(6) DEFAULT NULL,
  ADD KEY idx_resume_deleted_at (deleted_at);
```

- 列表/详情默认只吐 `deleted_at IS NULL` 的记录，仓储层统一过滤，调用方不用自己判。
- `status` 不新增 `DELETED` 值：状态机只表达解析流水线走到哪一步，可见性是记录级字段，混进去会让 worker 的幂等判断多一堆特例。
- 解析中的简历也能删：worker 下一跳按 id 查不到（已被滤掉）就收尾，不会把删除态覆盖回 PARSED。
- 恢复有两条路：`POST /{id}/restore` 显式撤销；或者重新上传同一份文件，`content_hash` 命中原行后自动复原。

### 4.3 改造 `interview_session`

```sql
ALTER TABLE interview_session
  ADD COLUMN question_count  INT NOT NULL DEFAULT 5,   -- 主问题数 N
  ADD COLUMN follow_up_limit INT NOT NULL DEFAULT 2;   -- 每主问题最多追问 M 次
-- turn_budget 保留为兼容列，语义改为 N*(1+M) 的上限
```

### 4.4 改造 `interview_turn`

```sql
ALTER TABLE interview_turn
  ADD COLUMN kind       VARCHAR(16) NOT NULL DEFAULT 'MAIN', -- MAIN / FOLLOW_UP
  ADD COLUMN parent_seq INT,                                  -- 追问挂在哪道主题下
  ADD COLUMN depth      INT NOT NULL DEFAULT 0;               -- 0=主问题，1..M=第几层追问
```

```json

    "type": "PROJECT",
    "title": "项目经历",

## 6. 后端设计

### 6.1 分析流水线（两段式）

```
parseStructured() ──> blocks ──> renderMarkdown() ──> resume_analysis.markdown
                                        │
                                        ├─ ① ModuleSplitAgent：blocks → 6 个模块（1 次调用）
                                        │
                                        └─ ② PointAnalysisAgent：逐模块 → 小点 + 点评 + 3 问（每模块 1 次）
                                                                  │
                                                                  └─ 锚点计算（本地，不调模型）
```

**为什么两段**：一次让模型输出"6 模块 × N 小点 × 3 问题"的 JSON 必然冗长易截断；拆开后单模块失败只重跑该模块。

**成本**：一份简历约 7 次调用、15–25k token，约 ¥0.02–0.05。分析在异步任务里跑，约 30–60 秒。

### 6.2 Agent 职责

| Agent | 输入 | 输出 | 代码级校验 |
|---|---|---|---|
| ModuleSplitAgent | 带 id 的块列表 | `[{type,title,blockIds}]` | type 必须在枚举内；blockIds 必须存在；空模块丢弃 |
| PointAnalysisAgent | 单模块文本 | `[{title,quote,level,comment,improvements,questions}]` | quote 必须能在模块原文中定位；questions 补齐/截断到 3 条 |

### 6.3 锚点算法（不调模型）

```
1. quote 在 block.text 中 indexOf → 命中即得 start/end
2. 未命中 → 归一化后（去空白、全半角）再找 → 命中则 start/end 取归一化区间映射回原串
3. 仍未命中 → blockId 取模块第一个块，start=0, end=block.text.length（段落级降级）
4. 定位失败的次数记日志，超过 30% 视为该次分析质量不合格，重跑一次
```

### 6.4 失败与重试

- 分析阶段失败：简历置 `FAILED`，`last_error` 写"第几模块失败"，重试 3 次（复用现有队列退避）
- 已存在 `resume_analysis` 时重跑：整个替换（`replace`），不做增量
- 上传重复文件：沿用 SHA-256 去重；若已有分析则直接复用

### 6.5 面试编排改造

```
创建会话：PlanAgent 从 analysis.modules[].points 里挑 N 个点 → 每个点一道主问题
答题：
  Evaluator 打分（沿用现有四维 + 证据）
  ├─ kind=MAIN 且 score < 阈值 且 depth < M  → InterviewerAgent.followUp(同一小点)  → kind=FOLLOW_UP
  ├─ kind=FOLLOW_UP 且 depth < M 且仍答得浅 → 继续追问
  └─ 否则 → 取下一个未覆盖的点出主问题；无剩余点 → 生成报告
结束：报告 = 逐题分数 + 每个小点的覆盖情况 + 总结（沿用 ReportAgent）
```

- 追问阈值默认 70，配置项 `panel.interview.follow-up-threshold`
- `M=0` 表示不追问
- 总轮次上限 `N × (1+M)`，实际通常更少

### 6.7 原版预览（1:1 还原上传的简历）

**问题**：批注页最早是把 `blocks` 用前端样式重新排一遍。字体、分栏、右对齐日期、照片位置全靠猜，
用户看到的和上传的文件对不上（"不够还原"），批注也因此失去了"指回原文"的意义。

**做法**：不再重排，直接把 PDF 每页渲染成图，批注以矩形叠在原文上。

```
KnowledgeObjectStore.read(objectKey) ──> byte[]
        │
        ├─ PdfPreview.renderPage(n, scale)  ──> PNG（默认 2.5x，限制 1–4）
        │      缓存 key：preview/{contentHash}/{scale}/page-{n}.png
        │
        └─ PdfPreview.pageTexts()           ──> 每页逐字符 TextPosition 矩形
                └─ locate(quote)            ──> 命中字符的矩形（按行合并）
```

`locate` 的匹配顺序（与 §6.3 的锚点算法同思路，只是输出矩形而不是 start/end）：

1. 归一化：去空白（含全角空格/零宽字符）、全角转半角、统一中英文标点
2. 整句精确命中 → 取字符矩形
3. 未命中 → 取最长前缀（≥8 字）做二分收缩，仍不行再丢掉最多 6 个开头字
4. 同一行内相邻字符合并成一个矩形：垂直中心差 ≤ 0.65×行高，水平间距 ≤ max(3, 2×行高)

**坐标与缩放**：接口返回 PDF 点（1/72 英寸），前端按 `rect / page.width|height` 换算成百分比，
所以页面缩放、换分辨率都不会错位，也不需要后端按设备像素重算。

**取舍**：

- 图里的文字不可选中/复制 —— 这是"原样呈现"的代价；原来的文本视图保留为「文本」页签
- DOCX/TXT/MD 暂不渲染原版，接口返回 `available=false` + 原因，前端自动留在文本视图
- 原图直接读对象存储里的原始字节，**已分析过的简历不需要重跑分析**就能看原版

**实测**（`黄洋简历.pdf`，615×870pt，2 页）：19/19 条批注引文全部定位成功，两页共 29 个矩形。

### 7.3 批注页交互（重点）

**布局**

```
┌─────────────────────────────┬──────────────────────┐
│  A4 纸张（700px）            │  批注栏（340px）      │
│  markdown blocks 渲染        │  按锚点 Y 逐条对齐    │
│  每块带 data-block-id        │  相近时允许重叠 46px  │
└─────────────────────────────┴──────────────────────┘
        └──── SVG 连线层：从纸张右缘横拉到卡片左缘 ────┘
```

**锚点渲染**

```
blockId → 找到对应 DOM 节点
quote   → 在节点文本里定位 start/end
        → 用 Range 包一层 <mark data-point-id="p1">
```

**悬浮联动**（2026-11-06 改版：批注卡不再堆成一条列表）

| 触发 | 效果 |
|---|---|
| 悬浮正文 `mark` | 右侧**同一行**的那张卡从「标题条」展开成全文，`z-40` 抬到最上层 |
| 悬浮批注卡 | 对应的句子 `mark` 变黄加深；其余正文**保持原样**（不再调暗/模糊） |
| 点击批注卡 | 平滑滚动到对应 `mark` |
| 未展开的卡 | 只露标题 + 一行引用，相近的卡按 46px 步进叠放，允许重叠 |
| level 着色 | STRONG 绿 / MEDIUM 琥珀 / WEAK 红，卡片左侧 3px 竖条 |

**为什么去掉「其余段落调暗」**：第一版把非当前段落 `opacity .35 + blur 1.5px`，
实际看简历时整页发灰、字都读不清。现在只在当前句上加黄色高亮，正文始终保持可读。

**性能与鲁棒性**

- 卡片 `top` 与连线只在 `resize`、字体加载、筛选切换时用 `ResizeObserver` + `requestAnimationFrame` 重算，hover 不重算
- 锚点定位失败 → 降级为段落级高亮，不隐藏批注
- 窄屏（< 1280px）卡片改为正文下方的常规流式列表，全部展开

**原版 / 文本双视图**

- 默认进「原版」：PDF 每页一张图 + 半透明高亮框；没定位到的批注卡按 46px 步进排到末尾，不压正文
- 「文本」保留原来的 blocks 渲染，可选中复制；切换不重新请求分析，只换渲染层
- 高亮框与卡片共用 hover 状态，悬浮任一侧都联动；连线只画在已定位的批注上
- 两个容易踩的布局坑：
  1. 网格列默认 `stretch`，右栏高度会先撑大左栏的测量值，测量结果又反过来撑高右栏（高度死循环）——纸张列必须 `self-start`
  2. 切到原版时高亮接口尚未返回，`mark` 全空，测量会把卡片全部按顺序堆叠——测量要依赖高亮结果再跑一次

### 7.4 SSE 复用

沿用已有的 `sseStream.ts` 工具，面试页订阅 `agent` / `question` / `evaluation` / `report` 事件。

### 7.5 简历编辑器接入

`public/resume-editor.html` 是一份自包含的编辑器（约 2800 行：排版变量、撤销栈、模板、导出 JSON/HTML/PDF），
状态存在浏览器 `localStorage`，不依赖后端。接入方式是**保留它自己的实现，只换壳**：

| 位置 | 做法 |
|---|---|
| 入口 | 简历库每张卡片 → `编辑` → `/resume-editor/:resumeId`；批注页右上角也放了同一个入口 |
| 路由 | `/resume-editor`（编辑器默认草稿，可当模板新建）与 `/resume-editor/:resumeId`（载入指定简历） |
| 版式 | `AppLayout` 对 `/resume-editor*` 去掉 `p-10` 与入场动画，改成 `h-screen overflow-hidden` |
| 页面 | `ResumeEditorPage` 用 iframe 加载 `/resume-editor.html?embed=1` |
| 内嵌态 | HTML 里加一段 `embed` 判定：隐藏重复的品牌块、顶栏 60px → 52px |
| 旧入口 | 直接访问 `/resume-editor.html` 会 `location.replace('/resume-editor')`；`?standalone=1` 保留单页模式 |

**简历 → 编辑器文档的映射**（`src/utils/resumeDocument.ts`）

编辑器不认 markdown，认的是自己的 DOM 契约（`header.resume-head > .name/.headline/.contact`、
`section[data-section-type] > .section-body > .entry`），所以按块类型还原：

| 解析结果 | 编辑器结构 |
|---|---|
| 首个 `TITLE`「张伟 - Java 后端开发工程师」 | 姓名 + 求职意向（按 ` - ` / `·` 切） |
| 紧跟的段落（含 电话/邮箱/@/年限） | `.contact`，`|` 换成 `·` |
| `TITLE`「工作经历 / 项目经历 / 教育背景 / 技能 / 证书」 | `section` + `data-section-type` |
| 其余 `TITLE`「2021.07-至今  某公司  高级后端工程师」 | `.entry-title` + `.entry-meta`（日期提取成 meta） |
| 段落按 `；` 拆 | `.bullets > li` |
| 技能行按 `,` 拆再合并 | 单条要点 `Java · Spring Boot · …` |

日期用 `2021.07` / `2021年7月` / `2021.07-至今` / `Panel 平台（2024.03-至今）` 四种写法验证过，
统一渲染成 `2021.07 – 至今`。注意月份后的 `-` 不能被月份吃掉，否则 `2020.07-2021.06` 会被截成
`meta=2020.07-`、`title=2021.06 某公司`。

**扁平文档降级**：DOCX 的解析结果带 `TITLE` 块，直接按标题分章；TXT / PDF 抽出来往往整篇都是
`PARAGRAPH`（没有标题块），这时改用关键词反推：短句命中「教育背景 / 实习经历 / 项目经历 / 专业技能」
就当章节标题，日期开头的行当条目，前几行里 2–4 个汉字当姓名、含电话/邮箱的行当联系方式。
实测 TXT（#3、#4）能正确还原成 教育背景 / 技能 / 工作经历。

PDF 的坑不在映射而在**抽取顺序**：两栏排版的 PDF 抽出来是左右栏穿插的，章节标题可能落在内容之后
（`黄洋简历.pdf` 就是这种情况）。这类文档会在编辑器顶部提示「段落顺序可能和原文不一致，建议核对」。

**互传方式**：iframe 加载完成后先 `postMessage({type:'panel:editor:ready'})`，父页面收到后把
`{type:'panel:editor:load', document, storageKey}` 推过去，编辑器调 `applyDocument()` 并保存。
每份简历存在 `panel-resume-editor:v1:resume-<id>`，与编辑器默认草稿（`panel-resume-editor:v1`）互不覆盖。

**尚未打通**（后来补上，见 7.6）：编辑结果只落在浏览器本地，没有回写后端 —— 要「改完再跑一遍分析 /
直接拿新版去面试」，需要一个 `PUT /resumes/{id}/content` 与重跑分析的接口。

### 7.6 保存与重跑：把「分析 → 修改 → 再分析」接成闭环

| 接口 | 作用 | 状态流 |
|---|---|---|
| `PUT /api/v1/interview/resumes/{id}/content` | 编辑器正文写回成新的原文（存成 `text/plain` + UTC 时间戳键），并投一条解析任务 | `202` → `PENDING` → `PARSING` → `ANALYZING` → `PARSED` |
| `POST /api/v1/interview/resumes/{id}/analyze` | 原文不变，只重跑解析与批注 | 同上 |

几个刻意的决定：

- **回写纯文本而不是 DOCX**：编辑器产出的本来就是文本，假装回写二进制只会让解析器多做一次无意义转换。
  文件名跟着改成 `.txt`，`content_hash` 按新正文重算，避免「同名不同内容」被当成同一份简历复用。
- **解析中再投任务直接 `409`**：`PARSING/ANALYZING` 时重复入队只会重复烧模型 token。
- **前端不轮询接口文档**：批注页拿到 `status != PARSED` 就每 3 秒重取，`PARSED` 后自动换成新批注；
  这期间旧批注保持可见（`resume_analysis` 只在分析成功时 `replace`），失败也不会把上一版弄丢。

**顺带修掉的一个真 bug**：`PointAnalysisAgent` 原先在「某模块一条小点都没产出」时抛异常。可提示词里明明
要求「跳过姓名、电话、邮箱」——于是只有个人信息的「个人介绍」模块零批注是**正确行为**，却被当成失败，
整份简历重试三次后置为 FAILED。现在零批注的模块直接跳过，只有所有模块都空才判失败。
（`zhangwei2-resume.txt` 重新分析时正好踩到这条。）

**回写必须幂等**，否则每存一次就烂一层。踩到的三个具体问题：

| 问题 | 现象 | 修法 |
|---|---|---|
| 要点带 `- ` 前缀 | 后端把短横线当正文，再进编辑器变成 `- - 内容` | 导出不写前缀 |
| 日期写在条目行尾 | 只认「日期开头」，存回去后日期沉进标题、meta 为空 | 加 `TRAILING_DATE`（行尾日期，限 48 字） |
| 标题尾部残留分隔符 | 「某公司 · 后端工程师 ·」 | `tidyTitle()` 剪掉两端分隔符 |

`panel-fixture.txt` 连续保存两次后 blocks 仍为 14 条、文本逐字相同，往返已经稳定。

### 7.7 PDF 原样编辑：底板是原文件，改的是整块

7.5 里的编辑器是把解析文本**重新排版**一遍，看起来像一份新简历，而不是用户上传的那份。要的是
「渲染成和 PDF 一模一样的样式，然后在上面改」。做法是两层叠出来的：

| 层 | 来源 | 作用 |
|---|---|---|
| 底图 | `PdfPreview.renderPage(page, 2.5)` 的 PNG | 像素级还原原文件（版式、字体、校徽、照片全都在） |
| 分隔条 | 前端按 `sections[].heading` 画的横条 | 板块标题（教育背景、实习经历……）统一画成一条，样式全局一份 |
| 高亮层 | `PdfEditCanvas` 里按板块矩形绝对定位的透明按钮 | 鼠标移上去显示「实习经历 · 点击编辑」，点中高亮这一块 |
| 编辑框 | `PdfEditCanvas` 底部的抽屉 | 点中板块后从下面弹出，整块内容在这里改，页面本身一个像素都不动 |

**为什么按「块」而不是按「行」**：一行一行改看着精确，实际不可用——用户把字号调大一点，断行就全错位，
而且一段话要改就得逐行改一遍。所以版式分析只负责把页面切成**板块**（`PdfPreview.sections()`）：

- 用 `PDFTextStripper` 的 `writeString` 回调切出视觉行（`LineBox`，带 `x/y/width/height/size`）；
- 一页里出现 `HEADINGS` 白名单里的行（教育背景 / 实习经历 / 项目经验 / 专业技能 / 荣誉证书 …）就是板块起点，
  两个标题之间算一块；第 1 页页首没有标题的那块叫「个人信息」；
- **跨页要接回去**：上一页写到一半的板块，下一页开头那几行没有标题，不能单独成块——直接并进上一块，
  一块就有两个 `Part`（两页各一段矩形）。否则「实习经历」会被切成"正文一块 + 接上页一块"，
  用户点哪块都改不全（这是第一版实测踩到的坑，`mergesCrossPageContinuationIntoPreviousSection` 钉住它）；
- 板块矩形：有标题的段按整行宽度框（背后那条底色带一起盖掉），没标题的段只框文字本身（别把照片、校徽一起抹了）；
- 前端再把行拼回段落（顶到右边界 → 是被折行折断的；单独的 `•` 并进下一行），生成一段排版接近原文的 HTML 种子。

**标题不算正文**：`sections()` 把标题行单独摘出来放进 `heading`（一条整行宽、比标题行高一点点的矩形），
正文 `lines` 从标题下面一行开始，板块可点区域的上沿也卡在分隔条下沿 +2pt，标题不会混进编辑框让人误改。
前端拿 `heading` 画一条统一的横条（正好盖住原件那条底色带），**底色 / 文字颜色 / 字号全局一份**，
存在本机 `localStorage` 的 `panel-editor-divider:v1`，从右上角「版式」调；调一次所有标题跟着变，
所以「教育背景」和「技能特长」永远长得一样，不会一块深一块浅。

标题不给人改是有意的：改标题等于改简历结构，牵动的是解析和批注的分块；字号/颜色这些"看起来统一"的诉求
用分隔条满足，不必动文字。

至于**存下来的正文**，标题还是要有——否则重新解析时模型不知道哪几行属于哪一块。`getText()` 会给有 `heading`
的板块补回一行标题（`个人信息`、`全部内容` 是切出来的，原件里没这一行，不补）。视觉行拼文本时单独一个 `•`
的行并进下一行，不让它自己占一行。

点中板块后：**下面弹出编辑框**（页面高度 48% 的抽屉），里面是这一块的全部内容，`contentEditable` 富文本，
工具条给**加粗 / 斜体 / 下划线 / 字号（10–32）/ 字体（雅黑/宋体/黑体/楷体/等线）/ 颜色 / 插入图片 / 清除格式 /
完成 / 取消**。字号字体是给选区包 `<span style>` 实现的（不走 `execCommand`，所以点工具条不会因为失焦丢选区），
没选中文字时改整块；插入图片走 `FileReader` → data URL，直接存在板块 HTML 里。回车、空格、复制粘贴都是浏览器的
原生行为，就是 Word 的习惯。按 `Esc` 等同「完成」。

**为什么不在原位置改**（第一版就是那么做的，被否了）：PDF 的排版是死的，就地长出来的白卡片会盖住下面的板块，
宽度又只有正文那一栏，调个字号就挤成一团。挪到下面的抽屉里，宽度够、字能放大、也不会挡住原件——
页面只负责"这是哪一块"，改在别处发生。

**编辑框里的字必须和上面那张纸长得一样**，否则"改"这件事本身就很别扭。四个方面分别解决：

| 维度 | 做法 |
|---|---|
| 字体 | **直接用 PDF 里嵌的那份字体文件**：后端把 `FontFile2/3` 的字节吐出来（`/preview/fonts/{family}`），前端用 `FontFace` 装成 `@font-face`，家族名是字体内容的哈希（`PanelFont_37ba479a`），存进 `edit_layer` 也认得出。光按名字映射系统字体是不够的：这份简历存的字体名叫 `KaiTi`，系统楷体和它渲染出来并不一样 |
| 行内混排 | 一行按字体切成若干段（`LineBox.runs`）：`电　　话：` 是楷体、`13450150516` 是 Arial，编辑框里用 `<span>` 分别还原；有中文的行以"中文那个字体"为准，否则英文单词一多，整行会被判成 Arial，中文再退化成系统无衬线 |
| 字号 | **不能直接用 `getFontSizeInPt()`**：这份简历的 `Tf` 写 14，实际渲染只有 9.7——文字矩阵里带了 0.7 的缩放。改成量"全角字的字宽"（中文一个字就是一 em），纯英文/数字的行量不出来，用全篇中文行量出的比例补 |
| 行距 | 按 PDF 里相邻视觉行的基线间距中位数（14.6pt / 9.7pt ≈ 1.5 倍），且只统计"字号相近的两行"，否则个人信息那种 24pt 名字 / 20pt 标题 / 14pt 正文混排会把行距拉成三倍；结果再夹在 1.05~2.2 倍字号之间 |
| 版面 | 编辑框按"和这一页同宽、同倍数"铺一张纸（宽 = 页宽 × 当前缩放，左右各留 24pt），所以字号、每行能放几个字都对得上 |

前端把这张纸的宽度和字号都乘上当前缩放，等于把 PDF 那一页"搬"到下面来改；标题的字号/字体同理。
嵌入字体是**子集**（只有简历里出现过的字），用户新打的字会按字回退到后面的系统字体，所以 `font-family`
里必须保留 `KaiTi, 'Kaiti SC', …, serif` 这串兜底。

**加粗**：这份简历实测全篇 `Tr 0`（只填充、不描边），字体里也没有 Bold 变体，所以没有“假粗体”要还原；
真遇到用描边画粗的 PDF，目前识别不出来，用户点一下工具条的 B 即可，不影响文字。

**坐标为什么「点当像素」**：页面容器按 `page.width × zoom` 渲染，板块框用 `left = x*zoom`（宽高同理），
底图是 2.5 倍渲染，所以放大也清楚。默认 `zoom` 是适应容器宽度（实测 A4 简历在 1440 宽下约 174%），
加减号可手动调、`适应宽度` 复位；编辑框开着时这组控件挪到抽屉的工具条里，不挡页面。

**看到的改动要能留住**，这是比渲染更麻烦的一半：

| 存什么 | 存哪 | 为什么 |
|---|---|---|
| 原件 | `resume.source_object_key` / `source_content_type` | 回写会把 `object_key` 换成新 `.txt`，原件不能被覆盖，否则再打开编辑器就没底图了 |
| 正文 | 原有 `object_key`（新 `.txt`） | 重新解析走的是文本，不是 PDF |
| 板块改动 | `resume.edit_layer`（JSON：板块序号 → 富文本 HTML，`MEDIUMTEXT`） | 底图永远是原件，所以「哪块被改成了什么」必须单独记，换浏览器打开也能还原；用 HTML 是因为改的不只是字，还有字号/颜色/图片 |

`getText()` / `getEdits()` **直接读 DOM**而不是读 React state：点「保存」时最后一次编辑往往刚好在 blur 那一帧，
读 state 会拿到旧值，保存成功但改动丢了。

`edit_layer` 从 `TEXT` 改成了 `MEDIUMTEXT`（插图是 base64）。Hibernate 的 `ddl-auto: update` 不会把已有的
`TEXT` 列改成 `MEDIUMTEXT`，老库要手动跑一次：

```sql
ALTER TABLE resume MODIFY COLUMN edit_layer MEDIUMTEXT NULL;
```

服务端还加了两道闸：板块数 ≤ 200、改动 HTML 总计 ≤ 8 MB —— 插图是内联的，不设上限一个请求就能把库撑爆。
另外解析任务结束时现在会**核对原文指针**：解析要跑几十秒，期间用户又保存了一版的话，这次的结果直接丢弃、
不写回（以前会把手上的旧 `object_key` 覆盖回去，用户看到"保存成功"，其实改动被抹掉了）。

老数据没有 `source_*` 字段，`replaceSource()` 在第一次覆盖前补一次快照；`getSourceObjectKey()` 在没有值时
退回 `objectKey`，行为与改造前一致。`edit_layer` 解析失败按「没有改动」处理，坏 JSON 不会把编辑器挡住。

**接口**：`GET /api/v1/interview/resumes/{id}/preview/text` → `{available, reason, pages, sections, edits}`；
非 PDF 返回 `available=false`，前端换用结构化编辑器（`StructuredEditor`，即 7.5 那套 iframe）。
保存仍走 `PUT /content`，多带一个 `edits` 字段（板块序号 → 富文本 HTML）。

**入口收敛**：侧边栏的「简历编辑器」去掉了 —— 编辑器必须绑定一份具体简历才有意义。现在只能从「简历库 →
编辑」或批注页的「编辑」进入；直接访问 `/resume-editor` 会重定向回 `/resumes`。

**已知限制**（都写在这里，避免当成 bug 反复查）：

- 扫描件（没有文字层的 PDF）拿不到 `sections`，会退回结构化编辑器；
- 页面永远是原件：改过的板块只在原处打「已编辑」标（淡紫底 + 徽标），**看不到改后的样子**——
  要看内容就再点开一次编辑框。这是"底图不可改"的直接结果，换来的是永远不会盖住别的板块；
- 分隔条只改外观不改字：标题文字要改得回到原件（后面做"生成新 PDF"时再放开）；
- 分隔条配置存在本机（换浏览器/清缓存会回到默认），因为它是「看着顺眼」的偏好，不跟着简历走；
- 编辑框里是系统字体 + 重排后的行距，和原文件的字距不完全一致；
- 编辑后 `quote` 跟着新文本走，高亮定位按新文本匹配，改过的句子可能定位不到（批注页对缺失的点做降级排版）。

验证用的都是真文件：`黄洋简历.pdf`（2 页 / 615×870pt / 100 个视觉行 → **6 个**板块：个人信息、教育背景、
实习经历（跨页，41 行 / 两段矩形）、项目经验、技能特长、荣誉证书）。改「实习经历」一块 → 保存 → 解析完成后
`edit_layer` 存住 3.6 KB HTML，正文里同时能看到第 2 页续写的那句和补写的新句子，批注跟着重建；
重开编辑器仍是改过的样子（`edit_layer` 生效），验完再把正文与 `edit_layer` 一并还原。

## 9. 风险登记

| 风险 | 影响 | 概率 | 对策 |
|---|---|---|---|
| 模型引用 quote 与原文不一致 | 锚点定位失败，批注飘移 | 高 | 归一化匹配 + 段落级降级 + 失败率监控 |

| 追问导致轮次爆炸 | 用户疲劳 | 低 | M 上限 3，总轮次硬上限 |

## 10. 测试计划

### 单元测试（后端）

| 用例 | 断言 |
|---|---|
| `ResumeMarkdownRenderer` 标题层级 | `level=1` → `#`，`level=2` → `##` |
| 锚点定位 | quote 命中返回正确 start/end；未命中降级到块首 |
| `InterviewService` 追问计数 | M=2 时第 3 次不再追问 |
| 分数重算 | 总分 = 逐题平均，不取模型自报 |

### 手工验收（全链路）

1. 上传 DOCX / PDF / TXT / MD 各一份 → 状态都到 PARSED
2. 批注页：至少 3 个模块、10 个点，每个点 3 个问题
3. 原版视图与上传的 PDF 逐页一致（照片、分栏、右对齐日期），批注框贴合原文；DOCX/TXT 自动回退文本视图
4. 悬浮任意批注 → 原文对应行高亮（原版视图为高亮框），正文保持可读；卡片与原文双向联动
5. 缩放浏览器到 80% / 120% → 高亮框与连线都不错位
6. 设置 N=3/M=2，答得好 → 3 轮结束；答得差 → 追问出现且不超过 2 次
7. 历史页能看到这场面试并打开报告
